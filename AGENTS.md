# OAM Concurrent Execution Contract

## RSC Personal Warehouse Product Baseline

- For every task that designs, changes, tests, reviews, migrates, or deploys `cloud_oam`, first read `docs/RSC个人仓与物资运营扩展系统_正式生产版需求与架构设计_V1.0.md` completely before taking task actions.
- All code, database migrations, tests, documents, plans, menus, permissions, states, and acceptance criteria for `cloud_oam` must follow that baseline unless the user explicitly changes a requirement in the current task.
- Treat the baseline as product requirements, not as authorization to write to OAM, RSC, Workflow, Feishu, production databases, or other external systems. The operational safety rules below continue to apply.
- When current code conflicts with the baseline, report the gap and implement the smallest production-safe migration path; do not silently preserve prototype behavior.
- Keep approval, allocation, reservation, outbound, shipment, logistics signature, OAM receipt, RSC/personal inbound, notification delivery, and reconciliation as separate states.

统一任务开场白：

> 请先阅读 Project 中的《RSC个人仓与物资运营扩展系统—正式生产版需求与架构设计 V1.0》。后续所有代码、文档、方案都必须严格遵循该文档。现在请执行以下任务：……

- Multiple OAM tasks may run at the same time.
- All Python OAM clients must read authentication through `work/oam_shared_session.py`.
- Never call the OAM login or captcha endpoints automatically. If the shared session is invalid, stop and report that the session must be refreshed.
- The canonical session is `work/oam_session.json`. `OAM_SESSION_FILE` may explicitly override it; the callback-service copy is fallback-only.
- Read-only queries do not take a global lock.
- Any OAM write must take a lock scoped to the exact business object, for example `oam_task_lock("material-apply", approval_number)`. Do not serialize unrelated documents or provinces.
- Never print, log, commit, or copy the raw OAM token. Use `oam_session_status()` when identity or token fingerprint diagnostics are needed.
- A browser account switch does not update the shared service session. Browser login and code/API session state are separate.
- Before declaring any OAM, RSC, Workflow, or Feishu login invalid, run `work/global_business_session_health.py` for the exact required components. Only an explicit live `auth_required` result may trigger a login request. DNS failures, timeouts, a missing page, a broken CDP tunnel, HTTP 200 alone, or a visible login page without a matching live probe are not authentication proof.
- OAM API tasks must require only `oam`; they must not stop because RSC, Workflow, or Feishu is unavailable. RSC and Workflow share the Windows Edge NIO SSO session through `http://127.0.0.1:9224`; never create a second Mac/Chrome RSC profile or use the retired `9226`, `relay.nio.com`, or fixed Mortise version settings.
- Automated jobs that need to report an authentication failure must call the health checker with `--consume-notification`. When `notification.notifyUser` is false, do not ask the user to log in again; another task already owns the single current reminder. Never automate OAM captcha/login or enterprise SSO/MFA submission.
- Any OAM replenishment analysis or write must load `work/oam_replenishment_policy.json` and enforce its material-level exclusions, substitutions, and required remarks.
- Every provincial OAM replenishment batch must keep at most one `waitingApproval` type-4 application per province. Before any write, scan both the good and old backpack target positions for the same replenishment batch. Never create a supplemental pending application for a province that already has a pending batch application; if a correction is required, exactly reread all same-batch pending applications, verify that none has progressed, withdraw them, and replace them with one merged application. Explicit work-order direct shipments with different business keys or recipient bindings are separate business objects and must not be force-merged.
- Every OAM service-provider transfer application (`type=4`) must call `validate_service_provider_transfer_material_rules()` from `work/oam_service_provider_transfer_guard.py` before `/material/apply/save`, then call `verify_post_submit_material_rules()` on the exact reread details and application info. For `ADQCOM0317`, treat it as a Mercedes custom card. An A-card becomes a B-card after being swiped, so applications should request A-cards by default. The requested quantity may be any positive integer; an even total and a 50/50 A/B split are not required. Use one material detail line with the remark `A卡`, and use the order remark format `桩码{实际桩码}，{数量}张A卡`. The pile code, quantity, material remark, and order remark must be verified after submission. Missing pile codes, non-positive quantities, or order/detail mismatches remain hard blockers.
- Every OAM service-provider transfer application (`type=4`) must enforce the `serviceProviderTransferAddressValidation` rule in `work/oam_replenishment_policy.json`. Select one current OAM address-book record and keep its province, city, district, and detailed address as one indivisible binding; never mix region IDs from one record with an address from another or use guessed/fallback region IDs. Before the write, call `work/oam_service_provider_transfer_guard.py` to hard-block incomplete, non-hierarchical, or mismatched bindings. After submission, reread the exact application and verify the returned province, city, district, and address against the same binding. A transport success without this reread is not completion, because a mismatched region and address can prevent warehouse printing and outbound processing.
- Replenishment province scope must be derived live from OAM positions used by `蔚来汽车销售服务有限公司` whose names contain `背包` and whose types are `goodPosition` or `oldPosition`. Do not generate province sheets from a national administrative list; resolve province from the position name before the warehouse name.
- Any replenishment analysis must include the latest three-month demand from the `星星备件需求提交` Feishu Base. Deduplicate it against OAM by exact work-order number plus material code, count only the positive quantity difference, and keep pure replenishment, return, cancellation, and unresolved-province rows in an audit review instead of demand.
- For replenishment material `ADQCOM0088`, use the material-detail remark `普通启停卡` by default and verify the exact remark in the post-submit reread. Do not pause for a card-type choice unless the user explicitly overrides the rule for a specific request.
- In the `星星备件需求提交` Feishu Base, the public form uses the native `备件明细` question. Each detail row contains the searchable SingleSelect field `物料号 / 备件名称` (`编码 | 名称`) plus `数量`, and one submission may contain multiple material rows. Preserve the legacy text field `物料号` and the hidden system link `物料资料库关联（系统）`; never delete historical records or replace either field. Before processing newly submitted rows, run `work/sync_feishu_material_form_compatibility_20260802.mjs` to resolve the selected code into the empty legacy and system-link fields. Stop without overwriting when the selected code, legacy code, and linked master record disagree.
