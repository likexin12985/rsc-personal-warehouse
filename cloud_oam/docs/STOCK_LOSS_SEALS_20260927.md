## 实现范围

新增 `stock_loss_request_seals`，独立保存本人来源位置、操作者及人员、授权版本、
请求 ID、请求引用、全局幂等键 hash、内容 hash、预检 hash 和创建时间。没有工单
字段，不复用退回封存表，也不虚构工单。封存是禁止原请求执行的记录，不是报损单、
库存变动、报废或通知事实。

封存服务先取得库存账本锁及当前身份锁，再精确回查原请求。原提交已经存在时，
只返回经过完整证明的原单；原封存已经存在时返回同一封存；摘要或位置不同则冲突。
只有没有原单、没有其他库存作业占用请求、没有孤立执行证据时，才写入不可变封存
与完整审计。当前提交权限和本人已建立的个人仓均须验证，读取权限不能创建封存。

回查接口增加 `sealed` 结果，仍保持 `retry_permitted=false`：旧请求永远不能执行。
是否开始新的预检和新请求属于后续客户端流程，不能自动重新提交原库存操作。
正式报损提交与封存 HTTP 写路由仍关闭；本批不种入生产报损权限。

0146 PostgreSQL 证明覆盖：

- 用户请求 ID 在报损、退回、取消、出库、发运、验收、入账及封存之间双向排他。
- 原幂等键不能被迟到库存交易、需求收货或发运复用。
- 完整审计必须同事务存在，操作者、时间、每个摘要与封存内容精确一致；不能后补
  同请求的库存审计或状态片段，以制造“已执行”的另一种结果。
- COMMIT 再验证当前身份、权限、保管关系及权限有效期，过期则整笔回滚。
- API 仅 SELECT/INSERT，无更新、删除、TRUNCATE 或私有证明函数直接执行权。
- 空库可升级/降级/再升级；有封存历史时拒绝降级，SQLite 插入保持关闭。

库存作业沿用库存账本的锁顺序。需求收货/发运的新增键互斥使用带固定命名空间的
事务 advisory lock；封存先取得身份锁再取得此键锁。该分支不新增全局库存账本锁，
无关审计和状态事件也在取得库存锁前退出。仍需完整 CI 检查与原业务的整体兼容性。

## 基线缺口复核与下一开发切片

本次按基线第 1.11、3.9、3.11 节重新核对实现，而不是以规划函数存在作为业务完成：

- `stock_operation_orders` 当前仍要求 `status='submitted'`。五种处置及区域/总部
  状态转换只有纯规划契约，没有持久审核事实和正式服务，不能通过直接改原单状态启用。
- 0145 的冻结保护累计原报损明细全量，并要求相关 SN 保持 active 且仍在原冻结账户。
  当前它正确阻止任何提前释放和报废；接入处置时，需要新的追加迁移以经过完整证明的
  同单处置流水扣减剩余份额，并验证原行、数量、SN、审核结果和流水一一对应。
- 优先补实际报损提交的权限在 COMMIT 前到期，以及两张报损单共享同一冻结账户的
  PG16 场景。封存到期和单申请冻结保护已有证明，不能代替这两个场景。
- 然后持久化区域核实与总部终审，执行当前权限/范围、禁止本人审批、重复请求精确
  回读和审核历史不可变。审批事实先独立成立；库存处置必须另有精确流水事实。
- 恢复可用、转旧件、转坏件分别生成同保管责任的反向/成色账户移动；退回只创建
  待退回事实并沿后续出库、发运、验收、入账解除责任；报废须总部批准和专用流水，
  同事务校验 SN 生命周期。误报/失而复得走专用反向单，不删除封存或原过账历史。
- 数量/SN 本机 PG16 专项尚未进入 GitHub 持续门禁。应使用独立的一次性夹具环境，
  不向已有业务历史的主门禁库强行降级，也不放宽正式保留约束以便测试运行。
