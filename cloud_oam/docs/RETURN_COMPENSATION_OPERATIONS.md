# 拒收退回补偿：0176 运维与验收说明

## 适用版本与业务事实

正式迁移为 `20261225_0176`，精确前驱为 `20261224_0175`。发布必须采用经过完整门禁的相同源码、镜像与迁移；本文件不是生产执行授权。当前验证终态及仍未开放的HTTP/页面见 `CONTINUE_DEVELOPMENT.md`，不能用旧候选结果替代正式发布验收。

同一批准明细可以同时存在正常个人仓入账、拒收退回补偿、未履约取消。三者分开核验：

1. 拒收登记、实物离开、承运交运、来源仓验收、来源仓库存入账各自保存事实。
2. 来源仓已入账的每一笔接受数量，由原申请人独立全量补偿取消；唯一入账引用防止重复取消。补偿不再次移动库存，不伪造个人仓入账。
3. 未履约占用先实际释放；所有待发运、在途、待入账、未回仓拒收及待补偿均处理完后，才能准确取消全部未履约剩余数量。
4. 每条批准明细全部个人入账或取消后，由有权限的管理员独立关闭。通知、OAM只读收货和对账状态不替代上述事实。

例如批准3件：个人仓入账1件，拒收1件实际回仓并补偿1件，剩余1件实际释放占用后取消。取消总量是2件，但未履约取消的原命令只包含1件。页面恢复请求必须同时核对这两个口径。

## 迁移与权限边界

- PostgreSQL 16由独立 `star_oam_migrator` 执行在线事务迁移，精确验证当前唯一版本、原目录、函数、所有者和ACL。迁移身份不得拥有超级用户、建库、建角色、复制或绕过RLS能力。
- 0176正式迁移使用摘要固定的22条SQL；不运行开发候选编译器，不导入可变应用metadata决定生产DDL。
- 新表 `material_request_return_compensations` 只向API角色授予SELECT/INSERT；UPDATE、DELETE、TRUNCATE被权限和不可变守卫拒绝。4个新私有函数不给API或PUBLIC直接EXECUTE。
- API启动核对完整运行目录；OAM入口readiness和采集角色也绑定同一head。不能只改版本号、关闭目录核验或授予多余权限绕过启动失败。
- SQLite仅作schema工具验证，新业务写入明确拒绝；它不是正式业务数据库。

## 结果未知和原请求恢复

客户端先保存原请求key、trace、输入和指纹，再提交一次。超时或断网时保留原请求，使用当前读取身份查询原key或trace，不自动重复提交。核验包括原需求、原入账来源、逐行数量、原证据摘要及完整审计链；写权限后来被撤销不影响仍具读取权限者恢复本人原请求，但不允许新写。

历史恢复使用只读审计快照，不申请审计头写锁。原命令数量与详情总取消不同可能是存在退回补偿，应使用版本2分区核对，不能简单放宽总量校验。错误来源、错误分区、权限变化或记录不完整时均保留原请求并停止新写。

## 回退和数据留存

空0176补偿表可以在完整目录检查后退到0175，恢复原函数及readiness；已有补偿事实时必须拒绝降级，数据库版本和全部业务事实保持不变。禁止删除补偿/取消/关闭记录、修改版本表、禁用守卫、改写旧迁移或使用CASCADE来通过降级。

应用回退与数据库降级是两个不同操作。存在0176历史时，回退应用也必须能验证当前0176目录和历史语义；旧镜像若不兼容应保持停止，使用经验证的兼容修复版本。备份恢复必须在隔离环境演练并核验业务流水、审计、SN和原请求恢复，不能仅以数据库容器healthy判定成功。

```sh

PYTHONPATH=backend:backend/tests .venv/bin/python scripts/run_local_pg16_fulfillment_checks.py --postgres-bin artifacts/pg16-native-20260920/install/bin --remaining-cancellation
```

前两项各覆盖数量/SN模式，新组合与原v1取消证据分别验证。检查进程exit0、每库stopped/passed/serverExitCode0、准确源码清单、正式head、运行准入和历史留存结果后才记录通过。重复运行前先读取最新交接，复用相同源码的已有结果和在运行进程。

这些本地结果不证明生产迁移、真实渠道、用户UAT、灾备指标或正式上线。发布仍需基线规定的授权、演练和书面验收。

## 正式数量接口接线（v67）

`GET /api/v1/material-requests/{id}` 的 `cancelled_qty` 合并经完整核验的未履约取消与已退回补偿，不修改原申请明细。`completion-quantities`采用同一总量；`remaining-fulfillment`返回严格`2.0`分区，分别展示`unfulfilled_cancelled_qty`、`return_compensated_qty`和`returned_pending_compensation_qty`。没有补偿的原0171审计/取消证据仍保留原`1.0`格式。

列表按当前可见需求批量探测退回入账与补偿，再逐个完整核验有事实的需求；无退回记录时读取次数不随页面行数增长。部分退回只移除不再适用的直接整单取消，并以剩余数量决定补货入口；有独立剩余取消命令时仍禁止新履约动作。证据损坏直接报错，不能显示为零。

公开剩余取消和独立关闭命令由服务端启用正式0176能力，请求体不能选择内部版本开关。读取在写入口关闭后仍可使用，并保持`no-store`。本轮原生HTTP验证见最新交接和v67日志；本说明不是测试通过声明。

后续页面接线依次覆盖：从本人原拒收明细选择退回来源，登记/撤销登记及独立出发和交运，当前来源仓责任人验收，预览准确成色/SN入账方案并独立过账，原申请人按已入账来源补偿，管理员在全部批准数量入账或取消后独立关闭。使用现有服务、严格DTO和原请求key/trace恢复，不要求用户手填UUID；不能把登记、交运、验收、入账、补偿或关闭合并成一个状态。


## 2026-10-06 原拒收退回入口

需求详情中原申请人可按原拒收验收单和物料选择“拒收退回”，数量物料填写本次退回量，SN物料勾选本次退回SN。撤销登记保留原记录并释放登记额度；已有实物发出后不能撤销，承运交接必须绑定该发出事实并填写真实时间、承运商和运单号。发出、交运均不改变库存。

浏览器先保存原请求后提交；连接中断时使用“只读核验原退回”，不要新建请求替代或清除浏览器记录。当前来源、完整历史和原输入指纹全部吻合后才清理。命令GET在写开关关闭时可用，恢复不依赖已撤销的写动作权限，但仍要求当前本人读取范围。

v69原生数量/SN通过仅证明本地正式迁移、真实HTTP与数据库业务链。v70已接来源仓公共验收/入账，真实浏览器/UAT仍未完成，不能作为正式上线或真实实物已回仓证据。

## 来源仓验收和入账（v70）

当前区域仓负责人或总部仓管理员从“退回收货与入库”进入“需求拒收退回：来源仓验收与入账”。页面只列当前负责仓库范围内已交承运的记录；请选择退回单/物料，不手工填数据库ID。

实物验收记录本次接受、拒收、短少和接受中破损；SN件必须按实物录入SKU、SN和二维码，异常必须绑定已上传凭证。短少不耗后续待收份额，破损是接受的子集。验收确认不会自动增加仓库库存。

已接受实物要另点“预览本次实物入账”，确认目标仓、成色数量和SN后提交。库存方案由服务器生成，客户端不选择或拼接账户。已入账记录显示独立事实，原申请人的退回补偿取消仍是后续单独操作。

提交前浏览器保存原请求；响应丢失后保留原记录，从“只读核验原请求”回读。未查到不代表失败，不得自动重发。撤销写权限但仍有当前仓读取权限者可恢复；责任仓/身份改变或历史无法核验时停止该对象，不清除原请求。原浏览器记录损坏需保留并人工排查。
