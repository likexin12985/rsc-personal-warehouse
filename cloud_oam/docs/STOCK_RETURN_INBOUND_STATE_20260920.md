# 按验收单回读入账状态与小程序恢复

2026-09-20，接续 7.42；工作树 `codex/notification-delivery-worker`。
本批为本地开发，未提交、推送、上传候选、部署或调用真实业务与通知供应商。

## 已实现的行为

新增 `GET /api/v1/stock-returns/my-receiving/{receipt_id}/inbound`，使用既有
`stock_operation.read` 及当前接收责任核验。返回本次验收的 `not_posted` 或 `posted`，
后者包含经完整事实验证的入账单号、流水标识、目标仓位与入账时间。
响应为 private/no-store，不返回原请求、计划摘要或幂等坐标。

查询重新验证原验收与 7.41 的完整入账事实图，检查前后库存/审计游标和当前权限。
没有 header 时还检查准确验收键的流水、入账明细和业务事件；发现孤立执行证据即拒绝确认，
不会仅凭缺少 header 显示未入账。封存是原请求的独立事实，不是验收单入账状态。
读取禁止自动 flush；已入账验收不再生成新的入账预览。

小程序内部退回收货页保留刷新前选择的验收单，显示入账单号与时间。
只有状态核验通过、存在接受数量、有当前写权限且本地恢复记录可用时才提供入账预览。
查询失败显示待核验并禁用提交。选择别的验收单不清除原请求的待核验记录。
隐藏、刷新、切换身份/权限或切换验收单时，迟到的回复不能覆盖当前页面。

确认提交前重新预检，并与用户看过的方案摘要比对；方案或授权版本变化须重新预览确认。
若其他设备已经完成入账，直接读取已完成记录。提交未知或原 GET 失败时保留恢复坐标，
即使验收状态显示已入账，也只有原请求的精确 GET 可以清除本地恢复记录。
原请求已封存或已入账的竞争结果都会触发页面刷新，不新增库存 POST。

联合检查还发现共享恢复模块给入账封存多传 `operator_person_id`，与该接口的严格 schema
不符。现在仅对独立入账发送 `request_hash`，其他业务的封存请求格式保持原契约。
使用实际小程序模块生成请求体，再经 FastAPI 提交和原 GET 回读，验证双方契约。

以上业务页面仍是内部源码：当前公开小程序只注册“交流备件知识大全”，没有将业务页加入
公开上传包。网站首页“星星后台管理”继续指向 `/xx`，首页不嵌入登录。
