## 本批业务范围

总部有当前`stock_operation.reverse_loss`权限的人员，可对准确的原报损派生退回执行整批停止，前提是尚未发生任何出库或后续履约事实。预览必须核对原处置、退回行、数量/SN、保管责任、权限和完整履约图；提交时重新校验，并与正常出库竞争同一业务锁。

停止事实及其反向库存交易同一事务提交，保留原报损、批准、退回和库存历史。停止先提交时出库必须被拒绝；出库先提交时整批停止必须被拒绝。不能通过删除原单、覆盖余额或修改物流状态实现停止。

部分出库、已发运、已收货、已入库、历史成色分类错误、报废和失而复得仍需各自的纠正或实物逆向流程，本批没有实现这些模式。旧退回历史仍按原来的六个履约阶段展示，停止事实单独呈现；历史结果不表示当前可用库存或当前写权限。

## 页面与接口

H5总部“报损纠正”的原退回处置提供专用停止区域：填写原因、预览、勾选确认后提交。首页仍为公开知识查询，星星管理按钮进入`/xx`；小程序的公开入口保持既定范围。

以下接口统一位于`/api/v1/stock-operations/loss-reports/corrections/return-stops`：

| 方法与相对路径 | 作用 | 当前业务权限 |
| --- | --- | --- |
| GET `/sources/{root_disposition_id}` | 读取准确原退回及独立停止历史 | 总部`stock_operation.read`及数据范围 |
| POST `/preview` | 核对整批未出库停止计划 | 总部`stock_operation.reverse_loss` |
| POST 根路径 | 原子停止、反向过账及请求绑定 | 同上 |
| POST `/request-lookup` | 只读回查原始请求 | 总部`stock_operation.read`及数据范围 |
| POST `/request-seal` | 显式永久封存未确认请求 | 总部`stock_operation.reverse_loss` |

读写权限分别判断。撤销写权限后，有合法读权限的人员仍可回查既有结果；读权限也撤销时不得继续展示敏感结果。合成测试中的授权不代表真实人员RBAC配置已验收。

## 网络中断和请求恢复

客户端在写入前保存完整原始命令和请求坐标。返回未知结果或503时保留该命令，使用原请求回查；不得自动重发，也不得因“未找到”而断言没有提交或开放重试。

- `found`：显示准确原始结果，保留原库存事实。
- `sealed`：原请求及受保护的坐标组合永久禁止执行；封存本身不改变库存。
- `not_found`：仍禁止自动重试。需要放弃该未知请求时，用户明确确认后请求封存；若服务端发现已经提交，则返回既有结果，不创建虚假的封存。

用户身份、原处置或存储内容变化时，旧预览失效；刷新失败不继续使用旧授权或旧来源。不同页面对同一原处置共用操作锁。新业务请求必须由用户明确发起并重新预览，不能作为未知请求的自动替代品。

新增`stock_loss_return_stops`记录与准确原处置、原退回及反向交易绑定。数据库延期约束校验整笔事务；停止、审计、状态事件或通知outbox不完整时必须整体回滚。API不能更新、删除或截断历史，也不能直接执行私有证明函数。

UUID扩展沿用0159的独立DBA引导。启动校验既检查扩展成员身份，也检查函数自身所在schema。不得通过授予API私有schema USAGE或函数EXECUTE绕过启动错误。

## 可重复验证入口

在`cloud_oam`目录运行：

```sh
.venv/bin/python scripts/run_local_pg16_return_stop_checks.py \
  --postgres-bin /absolute/path/to/postgresql16/bin --scenario seals
```

该入口只创建全新私有Unix socket PG16测试库，不接受既有DSN或数据目录。默认分别检查quantity和serial；可通过`--tracking`聚焦一个跟踪方式。需分别覆盖以下场景，不能用其中一项通过替代全部：

| scenario | 验证重点 |
| --- | --- |
| `seals` | 空库往返、永久封存、晚到身份变化回滚、原请求恢复及有历史拒降 |
| `http` | 正式注册接口、真实COMMIT后响应丢失、只读恢复、权限撤销和绑定异常 |
| `negative` | 畸形停止事务被数据库拒绝、准确库存反向变化和不可变保护 |
| `seal_first` / `execute_first` | 封存和执行的双向竞争、准确结果和互斥事实 |
| `stop_first` / `outbound_first` | 停止和正常出库的双向竞争、单一库存结果及SN归属 |

CI矩阵名称为`return_stop_`加上述scenario，每项分别覆盖quantity和serial。正式CI仍要求GitHub托管的可销毁PG16服务和明确准入；本地脚本不绕过此限制。本地证据必须同时核对退出码、业务检查、源码摘要及正常停库。CI分派测试、本地PG16及准确提交SHA的GitHub结果属于不同证据。
