## 问题与最终行为

真实 PG16 的 API 角色曾在事件 `FOR UPDATE` 处返回 42501；事件/收件人原只有 SELECT、
INSERT，而旧扩展器同时锁两张表并更新事件 status。前序失败与初步候选保留在
[7.76 原生通知专项](NOTIFICATION_OPERATIONS_PG16_20260921.md)。

0129 仅授予 `notification_events.status` 列 UPDATE，仍拒绝表级 UPDATE、收件人任意列
UPDATE 和事件内容写入。扩展器继续锁事件，以普通查询读取收件人；已有投递不会重复创建。
新增私有 invoker 触发函数和两个 ALWAYS trigger，并同步 API 安全清单、readiness 摘要、
当前迁移 HEAD、Edge 物料采集开通脚本和 CI 检查入口。

数据库状态规则：

- 允许状态不变、pending → expanded/cancelled、expanded → cancelled。
- expanded → pending 仅在该事件存在**已绑定原人员目标、active、且尚无投递记录**的收件人时允许。
  这保留了人工核实原目标身份后补齐渠道的独立恢复流程；没有把恢复绑定伪装成发送或送达。
- cancelled 不可恢复；无待展开原目标证据时，不允许将 expanded 改回 pending。
- 事件全部非 status 列不可改写；事件删除、TRUNCATE 均被数据库拒绝。历史正文不回填、不重写。

恢复服务先 flush 新收件人及原目标绑定，再切换事件状态，确保状态守卫读取到同一事务的
实际待展开证据；绑定、事件状态与审计仍是同一事务，失败全部回滚。

新增取消竞争检查又复现了 ORM 缓存缺陷：一个会话先读取 pending，等待另一个事务取消，
取得事件锁后仍使用缓存中的 pending。新守卫拦下了错误状态更新。扩展查询现在在取得行锁
时使用 `populate_existing=True` 刷新事件，返回 cancelled，且不创建投递。
