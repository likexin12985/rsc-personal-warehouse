# 分配后的供给计划管理

适用基线：正式 V1 的 1.7、1.8；当前前向数据库版本为 `20261227_0178`，前驱为 `20261226_0177`。下文保留0177既有计划管理的迁移说明。本文件说明候选实现与本地验证范围，不表示生产已迁移或上线。

## 用户可见行为

已完成最终审批且只有分配轴推进时，总部管理员可在原需求详情中更新、取消既有供给计划。更新参考号、预计日期、计划状态与处理原因；取消计划必须保留原参考号和预计日期。每次提交仍核对需求和任务版本、当前角色和授权。

计划操作不改变批准量、分配事实、占用、发运、收货、个人仓余额或通知状态。取消的是预计计划，不是撤销实际货源分配。部分分配可以连续发生；只有分配轴实际变化才生成状态转换，每笔分配均保留独立审计。

页面先保存原请求坐标，再提交一次。响应丢失后通过只读接口核验原结果，不自动重发。历史结果保留当时的状态，当前详情可以继续推进；只有完整证明历史与当前事实的关系后才清理恢复记录。

## 迁移与权限

0177 保持旧迁移不变，以原位函数替换更新三个函数正文：供给历史校验器、任务写入守卫、运行就绪检查。函数的 OID、属主、权限、安全执行模式和搜索路径由既有替换工具逐项验证并保留；不新增表、账号或执行授权。

必须区分两种旧限制：旧供给历史校验器要求审批之后的供给命令形成连续前缀；独立的任务写入守卫则直接禁止分配后更新任务。新迁移同时处理这两处，不能仅修改服务或按钮。

新的连续命令历史允许分配穿插在既有计划的更新、取消之间；核对逐笔分配事实、当前审批版本、历史操作者及角色有效时间、SKU/SN、数量上限、命令结果、独立审计与状态转换。其他履约命令尚不能穿插在这段计划历史中。旧记录升级后完整保留并重新验证。

数据库对供给命令与穿插分配命令的结果正文独立计算规范化 SHA256，摘要必须与正文一致。客户端提交成功后需要精确回读；历史结果恢复允许当前详情已发生后续分配，但不能仅因版本变大就认定原命令成功。

迁移只允许 PostgreSQL 16 的直接、非特权 migrator 在 read committed 事务中执行，要求精确单一前驱。运行入口核验当前版本和全部固定函数正文。SQLite 只用于结构工具链检查，不能替代 PostgreSQL 业务验收。

## 发布和回退

在未产生分配后的计划更新或取消记录时，0177 与 0176 可以执行经验证的迁移往返。产生此类记录后，降至 0176 必须拒绝，原版本和业务事实均保留。不要通过删除记录、禁用触发器、修改迁移版本号或覆写旧函数绕过留存检查；生产问题应使用保留历史的前向修复。

发布前还需当前源码完整门禁、发布验收和生产授权。隔离库的角色与数据为合成，不是生产环境配置、短信实发或真人 UAT 证据。

## 尚未开放的基线能力

- 占用、拣货、出库或发运之后的计划管理与历史恢复：须纳入各自独立命令和补偿历史，不能直接放开状态检查。
- 原计划操作者授权版本变化后的恢复：本次仍遵守原有身份和授权要求，不冒称已实现撤权恢复。
- 持久在线 PC/H5、真实用户和渠道验收、全量 CI、历史迁移、三日对账、性能和灾备验证仍独立待证。
