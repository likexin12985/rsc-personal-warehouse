## 按依赖推进

### P0：异常结果恢复

`0059–0061` PG16 全量迁移/并发/API 真链验收已通过；后续数据库变更仍须独立准确 SHA 门禁。
服务器明确拒绝与网络结果未知分开处理：只允许严格、可证明未落库的业务错误解除本次意图；
不能按所有 4xx、中文报错或 `not_observed` 统一清标。

后续“未执行封存”必须增加服务端持久证据并与原 POST 共用串行化边界：
原 POST 先提交则返回已提交事实；封存先提交则所有迟到 POST（含直接 SQL 绕过）均失败。
封存不得推进需求/任务版本、库存或十个状态轴；不能用 TTL 或多查几次代替提交级排他约束。
这是待实现方案，不是已具备能力。原 lifecycle v1 哨兵缺少人员/请求等锚点，不能自动猜测回填。

验收至少覆盖：响应丢失、提交前中断、重复封存、并发原 POST、身份变化、权限撤销、
旧哨兵、页面卸载及本地存储失败。未决操作永不自动生成新请求坐标。

### P0：首批建账和盘点入口

已有后端 `POST /v1/stocktakes/opening`，PC 期初页面仍需补启动入口；复盘人员选择不能依赖
人工填写 UUID。复用正式、授权过滤的主数据目录和现有版本/范围封印，不新增旁路写接口。
盘点意图的硬刷新/进程终止保护需单独补验，不能因供给恢复已实现而推定盘点同样具备。
期初盘点/对账错误和小程序页面已移除原始幂等键，核验提示仅保留非敏感追踪坐标，原始键
仅限原请求内存。仍需修复通用 4xx 清标、身份绑定、跨刷新持久化和小程序写后投影收口：
合法 POST 响应可确认历史命令，但不能在回读仍是旧范围 pending 或旧 approved 版本时清除阻断。

验收：角色/区域范围、范围快照确认、重复启动、复盘负责人筛选、盲盘不可泄漏应盘数量、
差异/复核/过账/对账/关闭独立状态及跨刷新恢复。

### P1：最小待办与业务通知

先呈现待盘点、待审批、供给计划和结果待核验，不建设完整 BI。
库存过账已原子写 outbox，不等于通知已送达；仍需正式通知展开、接收人快照、投递/尝试账本、
回执核验与可恢复 worker。登录短信及已购 1000 条套餐不能作为业务通知闭环证据。
外部供应商仅使用 fake/隔离适配器验证，正式联调需另有明确授权和外部条件。
现有 API 数据库角色不能推进通知投递和 Outbox 状态，需独立最小权限 worker 及前向迁移；
通知表的不可变证据、未知发送结果和可信回执约束尚需实现。
当前需求取消约束会将需求相关 NotificationEvent/Outbox 视为阻塞，首个通知切片应限于已有
盘点事件；未经前向兼容修复，不能直接给需求审批插入通知而改变其取消语义。
派生待办应复用各领域的实时 `allowed_actions`，不另建可编辑状态；没有审批 SLA 时不得编造超时。

验收：消息重复消费不重复发送、provider 接受与实际送达分离、超时/失败可追踪、
权限过滤、正文脱敏、库存和审批事务不依赖通知服务在线。
