## 2026-10-06 长期 PostgreSQL 浏览器联验入口

`scripts/run_local_pg16_fulfillment_checks.py` 已纳入可选 `--browser-tail`。
默认仍是数量/SN无人值守 HTTP 门禁；浏览器模式必须明确选择一个 tracking，不接受外部 DSN，
只在新建的隔离库里注入测试身份，运行真实应用/API数据库角色。先完成 warehouse 构建，然后在
`cloud_oam` 目录执行：

```sh
.venv/bin/python scripts/run_local_pg16_fulfillment_checks.py \
  --postgres-bin artifacts/pg16-native-20260920/install/bin \
  --tracking quantity --browser-tail
```

脚本先完成受控期初、审批和五步实际履约 HTTP，待 `browser-ready.json` 出现后打开其 URL。
在指定测试需求中登记收货、建立待入账单并过账；三个浏览器 POST 必须依次为201/201/200。
完成页面刷新、原请求回读和证据保存后，在该次运行目录创建 `STOP-BROWSER` 文件，脚本才继续
最终库存/SN回读、权限、历史保留拒降和停库检查。不要用新命令重放未知结果。

入口仅监听127.0.0.1:18087，限制Host、同源POST、当前测试需求的收货/入账及必要读取；
拒绝跨站访问、其他需求写入及其他业务动作。默认20分钟等待，`--browser-timeout`可设置60–3600秒；
超时失败并停止服务。真实源码、前端源码和构建均记录哈希并在结束前核验。
前端预览有测试身份提示，不能当持续上线入口或用户UAT。无需浏览器交互时不要传该选项。

新增内部 `material_request_inbound_history` 从不可变命令、审计链和实际库存移动证明入账，
`material_request_closure_coverage` 按明细计算批准−取消−已过账。长期真库门禁也核验这两个模块，
但它们不是关闭接口：剩余量取消事实、关闭权限/迁移及并发约束仍待完成。
最新逐次终态以 `CONTINUE_DEVELOPMENT.md` 和对应运行目录为准；下文保留早期验收范围，不累加为当前全量通过。

## 本批修复

此前入账命令将已经属于本账的在途账户作为来源，却使用仅允许外部进入的库存类型
`inbound`。真实统一过账服务会以 `external_inbound_direction_invalid` 拒绝该命令。
现在使用 `transfer`，从原出库事实的在途目标账户转入已预置的个人仓 `available` 账户。
合格数量已完成验收，不再入账到 `arrived_pending`；拒收数量不进入本次移动。
库存的法律所有组织、SKU、成色和批次沿用原来源事实。服务不创建或猜测目标账户。

已完成的入账单此前会在检查所属需求之前直接返回库存事务编号。现在所有调用先验证
需求、收货、发运与目标人员/位置绑定，再调用统一库存服务。相同命令和幂等键的重试
必须通过当前身份、库存账户范围和原请求指纹校验；不同幂等键不会被当成原命令成功。

入账使用需求在先、入账单在后的行锁顺序；已有 `inbound_postings` 绑定必须与统一
库存服务确认的事务一致。成功重试不追加第二个绑定。接口将领域错误映射为稳定的
403/409/412 等状态，并回滚失败事务，避免把可识别冲突误报为未处理的 500。

## 本地证据与边界

`tests/test_material_request_inbound_posting.py` 使用数量和 SN 两类实际 ORM 业务事实。
首笔库存提交在 fixture 中按统一服务的规范化请求指纹构造；之后的重试直接运行真实
`post_inventory_transaction`，包括真实当前身份和库存权限判断。覆盖：

- 相同命令重试返回原事务，不改变余额或增加绑定。
- 通过另一张已存在需求访问入账单被阻断。
- 撤销库存过账权限、变更身份版本后不能绕过校验。
- 新幂等键不能复用既有业务过账键。
- 目标人员变化、缺少个人仓可用账户时阻断。
- HTTP 领域错误稳定返回并回滚。

与既有收货/入账契约测试合计 24 项通过。扩大到物料需求与库存过账模块后为
617 passed、1 skipped，耗时 130.45 秒。该证据验证服务组合与重试边界，不声称验证了
真实 PostgreSQL 16 的首笔余额移动、并发锁等待或事务触发器；这些仍需准确 SHA 的真库门禁。
无数据库结构变更，不改写历史过账事实。

## 页面恢复证据

个人仓入账页在刷新后使用只读历史恢复待入账单，目标人员/位置从服务端事实重新填充；
未知结果进入阻断态，页面不会再次 POST。`只读核验原入账` 只重新读取需求的入账历史，
已过账时展示回读确认，仍待处理时保留阻断提示。前端专项 2 项通过；正式 Web 全量回归
54 个文件、1023 个用例通过，TypeScript 构建通过。

本批后续切入正式工单物料域时，入账表与工单操作表仍保持独立；个人仓过账不会自动生成工单
投料或消耗事实。
