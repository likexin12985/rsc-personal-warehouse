## 已验证的读取边界

- 只接受调用方提供的空闲连接，不读取凭据或外部 DSN，不导入应用配置。调用方已有事务时
  拒绝，不替调用方提交或回滚。连接必须为 PG16 的专用 `rsc_reconciliation_capture` 角色。
- 六张表固定为账本头、交易、流水、账户、库位和组织。候选检查 SELECT、无表写权限、
  无表所有权，以及无超级用户、角色继承/成员关系、建库、建角色、复制或 BYPASSRLS。
- 先以 `SET LOCAL` 设置超时，再取得六张表的 ACCESS SHARE 锁，最后才执行首次 SELECT，
  固定 REPEATABLE READ / READ ONLY 快照。头游标、流水及可变组织/库位信息取自同一视图。
- RLS 保持原状。恢复的应用数据中 `organizations` 启用并强制 RLS，本地只新增专用角色
  的 SELECT / USING true 策略；无策略、非完整读取策略或任何限制性 SELECT/ALL 策略即拒绝，
  包括针对当前未生效角色的限制性策略。不会把 RLS 过滤当成零库存。
- 对账本验证连续游标、posted 交易、连续明细、正数数量、唯一标识、有效端点和边界，
  对组织/库位验证父链、循环与引用完整性。SQL 自带行数上限，截断或超预算时拒绝整个结果。
- 账户资产所有组织与位置所属组织分别保留。候选不据此猜省份，地域映射仍待批准版本解析。
  输出固定实际采集时刻、数据库快照 ID、截止游标和内容摘要，明确标记授权、正式安全目录、
  地域解析和持久化尚未完成。不会读取余额投影来替代某一游标的历史流水。

PostgreSQL 的事务快照与锁语义依据[16 版事务隔离文档](https://www.postgresql.org/docs/16/transaction-iso.html)
及[LOCK 文档](https://www.postgresql.org/docs/16/sql-lock.html)。本地编译的 16.15 源码
`pquery.c / PlannedStmtRequiresSnapshot` 也已核对：事务控制、LOCK、SET 不固定事务快照，
首次 SELECT 会固定。单纯把锁移到后续校验前仍不足以消除以下已复现窗口。

## 实测发现与修正

1. 首次检查在恢复的应用 schema 上因 RLS 拒绝，原会话 `6364` 退出 1、实例停止。
   补充专用只读策略候选后，会话 `27608` 的原 12 项通过；该结果完整保留。
2. 代码复核发现原候选在锁表前执行 `SELECT set_config(...)`，提前固定了快照。新增真实
   PG16 并发夹具在首次 SELECT 与锁表之间提交过滤策略，实际 **3 个组织被读成 2 个**，
   旧快照的策略预检仍通过。会话 `45228` 退出 1，
   [缺行反例](../artifacts/daily-ledger-capture-20260921/pre-lock-policy-failure/pre-lock-policy-counterexample.json)
   及当时源码、结果均保留。
3. 改为不产生快照的 SET LOCAL、锁表，再进行首次 SELECT。最终会话 **72245 退出 0**，
   该并发策略准确被拒绝，原场景也全部通过，最终为 **13 项**，不累计历史尝试数量。

| 实际检查 | 结果与范围 |
| --- | --- |
| 完整应用备份恢复后的读取 | 沿用已验证合成备份，游标 3；3 笔交易、3 条流水、7 个账户、8 个位置、2 个组织；六表读取前后数量和摘要不变 |
| 真实并发提交 | 写方持有账本头行锁且尚未提交，读方不阻塞；头读取后提交新增交易及库位变更，旧快照仍为游标 1 / 原库位；随后读取为游标 2 / 新库位 |
| RLS 与权限拒绝 | 无完整策略、未生效角色的限制策略、锁前策略变更、误授 UPDATE、错误角色均拒绝 |
| 数据与事务拒绝 | 行数超限、缺游标、调用方已有事务均拒绝；调用方事务保持由调用方处理 |
| 超时与恢复 | DDL 排他锁触发 500ms 锁超时，慢语句触发 1 秒预算；错误后连接回到空闲，可再次完整读取 |
