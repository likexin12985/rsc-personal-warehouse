## 当前实现

- `file_integrity.py` 原样提取现行正式文件服务和 storage 的 **22 个**常量、类型及校验
  定义；定义摘要逐一一致，负向输入对照返回相同错误码/分类。独立进程导入不加载 app、
  Settings、SQLAlchemy 或 psycopg。正式落地必须让应用和 worker 共用这些定义，不能
  长期维护两份规则；当前生产文件尚未改变。
- `backup_worker.py` 只使用专用 OSS 读取配置，不接受 OAM、PG、POSTGRES 环境变量。
  检查任务目录 0700、所有者、准确输入集合，输入为同所有者的私有普通文件且无多重硬链接。
  对同一任务目录加排他非阻塞锁，并发 worker 在生成输出前被拒绝。
- worker 检查输入大小和可用空间，预留所配置容量的 8 倍给暂存/验证；下载、联合归档和
  完整校验后才写 `backup-complete.json`、输出摘要和私有 tar。校验失败清理本次生成文件，
  原始输入保持；已经完成的任务不能覆盖重跑。
- `joint_backup.py` 改用流式普通 tar 读取，不先收集全部成员；实际读取量、成员大小、
  类型、重复名称、允许名称和总预算分别校验。拒绝链接、稀疏成员、压缩外层、截断和异常
  大头；旧附件复制也有字节预算。
- `backup-entry.sh` 为未来 `scripts/backup.sh` 的候选。按数据库快照包、旧附件、专用
  worker 的顺序运行，只有三个步骤成功且主机再次校验 tar SHA256 后，才独占创建最终
  备份名。数据库口令经环境转交，不放入 argv 或 stdout。worker 的 stdout 位于任务输入
  目录之外，避免污染准确输入集合。
- `compose.backup.yml` 是未应用的配置片段：ops 服务、独立 egress 网络、只读根目录和
  脚本挂载、移除 capabilities、禁止提权，不连应用/数据库网络，不引入 app env_file。
  缺少备份凭据在实际运行 worker 时拒绝，不让未启用的 ops 凭据阻塞常规应用配置。

## 下一步必须处理的缺口

1. **导出阶段限额尚未实现。** 当前 `backup-entry.sh` 先写数据库快照包和 uploads 包，
   再进入 worker 做空间预检。这只能保护后续打包，不能防止前两次导出写满磁盘。正式
   落地前必须把空间/配置预检前置，并对导出生产端与主机接收端实施可验证限额；验证超过
   限额后的子进程、只读事务、表锁和暂存清理。不能仅在接收后检查文件大小。
2. 流式归档读取已有负向检查，但 catalog 仍在内存收集；512 MiB 配置、较大文件目录、
   大附件、生产历史量和 500 用户模型尚未做规模验收。不能将 8 倍磁盘预留当成内存或
   完整容量保证；应按真实规模改造/验证清单流式处理和资源参数。
3. 配置片段、脚本、纯校验模块和导出协议须在源码冻结结束后作为一组评审、接入和测试。
   必须同步切换正式应用到共用校验定义；不得只替换 dump.sh，让旧脚本把 tar 当 SQL。
4. 实际容器 UID/卷权限、网络隔离、超时/停止、专用 OSS 身份、bucket/region 绑定和
   KMS/真实恢复仍需验收。quarantined/deleted 留存策略、不同恢复 ETag 的审计证明、
   异地保管、生产 RPO/RTO 未关闭。
