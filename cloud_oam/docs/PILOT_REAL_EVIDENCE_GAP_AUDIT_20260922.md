## 3. 后续最值得开发的三项

### D1：将 prepare 与 start 绑定到同一份已核验工件（原始发现，后续修复见第 5 节）

定位：[deploy_pilot.sh](../scripts/deploy_pilot.sh)第 35–45、83–92、108–118 行；
[pilot_preflight.py](../scripts/pilot_preflight.py)第 195–208 行。

`prepare` 当前构建并迁移后仅输出成功；`start` 重新检查当前配置、确认名为 db 的服务运行，
随后按可变镜像标签启动。预检证明标签字符串正确，但没有持久化 prepare 回执，也没有检查
标签对应镜像 ID、候选源码与配置是否在两个阶段间发生变化。
例如，同一标签被重新指向另一镜像，或更换一份仍满足静态规则的配置，均没有跨阶段证据可以
证明 start 使用的就是 prepare 已验候选。这不否定现有隔离检查；它是执行单“同候选、同配置、
同项目且不重打标签”的要求尚依赖人工遵守。[部署专项](PILOT_DEPLOY_ENTRY_20260922.md)第 41 行已承认该边界。

独立行动：完整静态终端结束后，补原子写入的受控 prepare 回执，绑定项目、数据库/卷身份、
迁移 HEAD、三个镜像 ID/digest、候选清单及配置版本；start 先只读复核，不符则在启动 gate/API
前停止。保存脱敏公开元数据，任何涉及秘密的配置证明须留在权限受控文件中，不输出原始 env、
registry 内容或可用于离线猜测低熵秘密的单字段摘要。失配不自动重建、迁移、删卷或重发。
验证应覆盖标签重指向、配置漂移、错误项目/卷、缺失/损坏/半写回执和相同工件正常继续。

当天两侧采集/比较截止。因此不能把完成审核 UI 当作已有可运维的每日生产档案生成链路。

独立行动：复用上述核心，先做一次性受控 ops CLI（映射预览/核准/回读、截止 capture/recover）

或 migrator 配置放进 API/Web，不接受客户上传数量/快照或 DSN，不自动创建每日审批身份。
