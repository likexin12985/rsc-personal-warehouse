## 事务执行边界

入口接收服务端准备好的 owner、source reader、ledger reader 连接，校验 PostgreSQL 16、
相同配置数据库绑定和 idle 状态后才取得所有权。拒绝已有调用者事务时，不提交、回滚或关闭
该事务及其连接。正常接管后，三个连接为本次操作独占，结束时全部关闭，避免旧读取器事件
监听及超时配置影响下一次请求。

会话/业务锁、owner SQL、来源读取、本地采集、记录证明及提交前核验共用一份单调时钟预算。
每条 owner SQL 更新剩余 statement_timeout 和 idle_in_transaction_session_timeout；两个
现有读取器按剩余整秒分配预算，不向上取整或给下一阶段重新计时。COMMIT 不经过普通
SQLAlchemy execute 事件，因此提交前显式设置剩余 SQL 期限。

**此边界从三个连接就绪后开始。** 连接池排队、DNS、TCP/TLS/数据库建连尚未纳入；任意 Python
停顿也不能靠 SQL 计时器立即中断。受检数据库事务可在客户端停顿时按 idle timeout 回滚并
释放锁，正式部署仍须补建连和进程级整体期限，不能将本批称为完整 HTTP 请求期限已达标。

## 实际失败和恢复证据

| 场景 | 结果 |
| --- | --- |
| 会话记录被另一个事务锁住 | 2 秒预算，实际约 2.017 秒后 statement timeout；截止、审计及库存不变 |
| 账本 head 被另一个事务锁住 | 2 秒预算，实际约 2.028 秒后退出；无部分记录，所有本次后端 PID 消失 |
| 前阶段消耗预算 | 来源返回后模拟耗时，剩余不足一秒时拒绝开始本地读取，没有重置阶段预算 |
| 插入后、提交前客户端停顿 | 3 秒预算下模拟停顿，服务器 idle timeout 回滚；随后精确回读，失败请求不存在，旧记录保持 |
| 提交成功但客户端未得到确认 | 先实际执行 libpq COMMIT，再注入回执丢失异常。入口返回明确的结果未知错误；不自动重试，原请求回读找到准确记录且未增加重复记录 |
| 调用者已有事务 | 拒绝接管，原事务仍 active，三个连接均保持打开，随后由测试调用者自行清理 |

回执丢失是**合成观察故障**，不是本次真实网络故障。数据库实际提交和其后精确回读都已执行。
入口不能在 COMMIT 异常时宣称已回滚：此类情况统一要求原请求恢复。已经确认 COMMIT 成功
后，即使客户端时钟随后超过期限，也保留成功事实并附带超时观察，不能改报为未提交。

原 7.95 的伪造报表/流水拒绝、日期/摘要/权限、不可变记录、并发同请求、来源/映射撤销历史
恢复等场景全部经新入口再执行。每次已接管操作结束后，实际核对连接关闭和三个本次数据库
后端 PID 消失。四份完整截止及审计重新核对原始摘要、坐标、时间和独立数量计算。
