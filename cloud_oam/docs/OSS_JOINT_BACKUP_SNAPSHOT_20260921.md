- `formal_object_backup.py`：在[7.78 读取候选](OSS_OBJECT_BACKUP_CANDIDATE_20260921.md)基础上
  保留实际 HEAD 的完整规范化对象元数据，使恢复后的 ETag 和 head manifest 可重新核对。
  7.78 原文件及原始证据未覆盖。
- `verify_joint`：恢复前检查外层组件哈希、嵌套对象与数据库清单的准确关系、字节 SHA256、
  原 ETag/head 完成凭据及 pending 状态；数据库恢复前先验证全部包内容。

外层 manifest 声明 `database_catalog_bound=true`，来自同一快照协调流程。
内层对象包仍声明 `database_snapshot_bound=false`：它自身不负责数据库完整性；外层明确
绑定数据库清单、快照标识及所有组件。两层都不声称真实云端恢复已经通过。

## 实际 PostgreSQL 16 证据

使用 `backend/tests/local_pg16_cluster.py` 创建两套全新自有 PG16.15，迁移至
`20261108_0129`，仅私有 Unix socket，无 TCP。没有使用外部 DSN，没有重启旧数据目录。

源实例：`source-checks/run-pnfptk44`；恢复实例：`restore-checks/run-y9piqlt3`。
两者均已核验 `status=stopped`、`checks=passed`、`serverExitCode=0`。

实际链路：

1. 用现行正式服务建立有库存、SN、审计和来源审核凭据的合成业务样本，产生 **3 个已完成
   附件和 1 个 pending 意图**。对象内容使用仓库内合成 PNG，完成凭据由正式上传完成服务生成。
2. 以 `star_oam_backup` 执行候选备份入口，实际观察父级锁事务和快照事务仍存活。
   完整文件清单已经从导入快照导出，pg_dump 尚未开始读取。
3. 通过 API 角色完成原 pending 附件，再创建并完成另一附件并提交。此时源库 files 有
   **5 行**。仅 files、audit_events、audit_chain_heads 因这两个明确操作变化，其他事实不变。
4. 继续 pg_dump，导入同一快照 `00000004-00000007-1`。快照清单仍 **4 行**，原 pending
   仍为 pending，后建附件不存在。SDK 只下载快照中的 **3 个**可用对象，不读取后来可用的对象。
5. 生成、校验联合包，在全新实例恢复数据库。**206 张表、572 行**及序列/角色摘要与
   快照前的完整事实摘要一致。原 4 行文件状态与清单一致，不包含快照后的变化。
6. 恢复后重建库存数量和 SN 状态：3 条 movement、3 条 balance、4 个 SN 主档、1 个非空
   SN 当前位置均一致；3 条审计流、**64 条审计事件**验证通过。
7. API/Edge 数据库权限检查通过。3 个原上传主体可取下载意图，其他主体被拒绝，pending
   不可下载。原完成服务重新校验三个恢复对象的 ETag/head 凭据，所有探测审计均回滚；
   再次完整事实对比不变。这是本地对象夹具恢复，不能代替真实云恢复。
8. 清单导出成功后人为令 pg_dump 子进程失败，现行父级检查拒绝快照包，stdout 为 0 字节，
   临时目录清空；此前已完成联合包的 SHA256 保持一致。
