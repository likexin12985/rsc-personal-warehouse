# 首次通知的正式渠道身份核验

7.38 接续 [原目标恢复](NOTIFICATION_TARGET_RECOVERY_20260920.md)。原首次通知入口直接使用
账号 mobile 和任意应用中最近登录的 WechatIdentity，而显式恢复已经要求正式身份证明，
两条路径的边界不一致。本批统一它们的解析规则，所有原业务通知调用方均使用该公共入口。

## 当前实现

- `notification_identities.py` 提供共同的身份域配置与只读解析；事件创建和目标恢复都使用它。
  短信身份域来自启用的 PNVS 登录配置，微信身份域来自启用的微信 app ID；mock/disabled
  配置不能隐式提供生产通知渠道，解析过程不构造 adapter 或发起网络调用。
- 原 person_id 必须对应唯一有效账号和在职人员；当前正式身份必须能产生有效的正式权限上下文。
  手机号/OpenID 只是待核验坐标，必须精确匹配同类型、同 provider/app、同版本 HMAC 的
  AuthIdentity，且已验证、未撤销、验证时间不在未来。
- 微信只查询配置 app 的唯一映射，不选择其他应用的最近登录，也不以 UnionID 或手机替代 OpenID。
  精确查找后再次核验所读取的身份行，拒绝在查找与后续读取之间已撤销或改变的证明。
- 缺少配置、账号、有效角色或渠道证明时，只保留原通知事件和原人员目标，接收项为零；业务
  事实仍在调用方原事务内保存。真正的数据库异常仍交调用方回滚，不被伪装成“缺渠道”。
- 解析不 flush、不 commit、不写身份；如果调用方尚有未 checkpoint 的身份/权限图修改，
  本次暂缓解析，避免正式权限加载时覆盖 ORM 中的待写内容。无关 Outbox 的待写边界保持不变。
- 旧事件重放返回原接收项，不因身份后来补齐而自动补发；已留存的未绑定目标仍通过显式恢复处理。

本批没有新增表、迁移或权限，head 仍为 `20261019_0109`。这次解析证明的是创建接收项时
观察到的正式身份；**还没有新增不可变的渠道验证事实，也没有实现发送前的当前身份/provider
复核或订阅授权验证**。并发或之后发生的撤销、应用切换、密钥轮换仍必须在真实发送边界处理。
既有接收项不能仅凭存在就放行真实 adapter；不把本批写成 N1 全部关闭。
