# 0052/0053/0054 期初盘点证据链发布清单

本清单定义 `20260903_0052` 期初盘点证据链，以及两个不得回写历史迁移的必需前向修复
`20260904_0053`、`20260904_0054` 的预生产和生产发布边界，不授权连接或修改任何 OAM、RSC、
Workflow、飞书或生产环境。所有真实发布仍须经过变更审批、双人复核、备份恢复演练和
PostgreSQL 16 发布门禁；当前 `0054` 尚未取得对应准确 Git SHA 的远端 PostgreSQL 16 门禁成功证据，
不得写成已放行。

## 1. 不支持混合版本滚动

`0052` 为每个盘点范围完成事实增加不可变的原始请求文档 `request_jsonb` 和解析结果文档
`request_resolution_jsonb`，并由 PostgreSQL 约束请求、观测、盘点行、序列号、复核、过账、
对账和关闭之间的因果关系。`0053` 修复该证据链十五表共享延迟触发器的表分派：非
`stocktake_rounds` 记录不得解析轮次专属字段；它不改变业务状态、函数身份、ACL 或触发器绑定。
`0054` 只修复复盘建立后对其已封印来源初盘轮执行历史复证的语义：当前轮证明继续禁止提前存在
复盘范围分配，历史来源轮证明则允许观察由复盘图独立封印的后继分配。该迁移仅原位替换一个
既有 helper 和 readiness 的精确函数源，保持函数 OID、签名、所有者、ACL、六个调用方及触发器
绑定，不新增或修改表、业务行和权限，也不放宽当前提交证明。

| 应用版本 | 数据库版本 | 结果 |
| --- | --- | --- |
| 旧应用 | `0051` | 仅代表升级前状态，不具备 `0052` 证据链 |
| 新应用 | `0051` | 写入会引用不存在的列，失败关闭 |
| 旧应用 | `0052` / `0053` / `0054` | 无法生成两份必需证据文档，期初盘点写入被数据库拒绝 |
| 新应用 | `0052` | 共享触发器仍可能在非轮次记录上失败，不得停留 |
| 新应用 | `0053` | 有效复盘会在历史来源初盘轮复证时被拒绝，不得停留 |
| 新应用 | `0054` | 当前唯一受支持组合，仍须通过对应 Git SHA 的发布门禁后方可放行 |

因此禁止边迁移边保留旧实例处理盘点写请求，也禁止先发布新客户端或新后端再迁移数据库。

## 2. 维护窗口顺序

1. 记录待发布 Git SHA、容器镜像摘要、当前 Alembic revision 和变更单号，确认只有一个
   Alembic head。
2. 在 disposable PostgreSQL 16 和预生产先通过完整 release gate，并完成从真实结构脱敏副本
   的升级、备份、恢复和失败重试演练；不得用 SQLite 或本地跳过项替代。
3. 阻断 PC、小程序、API、Worker 和运维脚本的全部盘点变更入口，至少覆盖开始、实盘、补盘、
   复核、复盘、终结、过账、对账和关闭；允许与盘点无关的只读流量时，仍须确认它不会持有
   `0052` / `0053` / `0054` 所锁定表的长事务。
4. 等待所有既有盘点写事务结束，确认没有旧应用实例、离线队列或重试任务仍可提交盘点写入。
5. 使用正式备份身份生成一致性备份并验证清单；记录恢复点。备份未完成或恢复演练未通过时停止。
6. 仅由迁移角色执行 `alembic upgrade 20260904_0054`（或在已确认唯一 head 后执行
   `alembic upgrade head`）。迁移链先由 `0052` 保守回填可证明的历史请求证据，由 `0053`
   修复表分派，再由 `0054` 修复历史来源轮复证；若数据库已在 `0053`，仍必须保持盘点写入口
   冻结并排空旧事务后单独前进到 `0054`。`0054` 会锁定完整期初写边界并精确核验旧 helper、
   readiness、六个调用方、函数 hash/所有者/ACL 和触发器绑定，再原位替换函数源；任一历史事实
   无法唯一证明或 catalog/hash/ACL/触发器绑定不符时必须整体失败，不得手工补猜、置空、删除
   业务行，也不得改写 `0052` 或 `0053` 后强行通过。
7. 复核数据库 revision、正式函数体哈希、触发器、延迟约束、所有者和最小 ACL，再一次性替换
   全部后端实例为同一已验收镜像；不得保留旧实例参与流量。盘点写事务必须保持 PostgreSQL
   `READ COMMITTED`，`0052` 会拒绝其他隔离级别，不能通过会话参数绕过同轮次 SN 别名锁。
8. 只读检查 `/api/health/live` 与 `/api/health/ready`，随后在预生产或获准的隔离验收范围执行
   期初盘点零库存、批次、序列号、未知物料观测和篡改拒绝用例。健康检查成功不能替代业务验收。
9. 确认请求文档、解析文档、观测、盘点行及序列号集合可重放一致，并确认审批、分配、占用、
   出库、发货、物流签收、OAM 收货、RSC/个人仓入库、通知送达和对账同步仍是独立状态。
10. 解除盘点写入维护窗口，持续观察数据库约束拒绝、死锁、超时、审计链和 readiness；任何异常
    先重新读取准确事实，再决定前向修复或整库恢复，禁止盲目重试写入。

## 3. 回滚与降级边界

- PostgreSQL 的 `0054 -> 0053` 只允许在没有任何期初任务或保留期初证据的空历史场景执行；该
  降级会恢复 `0053` 的精确 helper/readiness 源，也会重新引入有效复盘无法提交的已知缺陷，不能
  作为仍承载期初业务的应用回滚路径。进一步的 `0053 -> 0052` 以及 `0052 -> 0051` 同样只用于
  没有 `0052` 证据或期初盘点事实的空历史场景，发现任一不可丢失的 opening graph 时必须拒绝。
- SQLite 的 `0054 -> 0053` 和 `0053 -> 0052` 仅推进 revision，`0052 -> 0051` 只检查两份请求
  证据列；SQLite 不存在这些 PostgreSQL 函数，不能证明函数源、OID、调用方、锁或降级安全，
  也不得替代 PostgreSQL 16 演练。
- 一旦迁移回填了证据或新版应用提交了任何相关事实，不得通过清空列、删除盘点行、关闭触发器、
  修改函数或强制执行 Alembic 降级来回滚。
- `0052`、`0053` 已属于迁移历史，必须保持文件和 revision 身份不变；`0054` 是唯一允许承载本次
  修复的前向迁移，禁止把同一改动倒灌进旧迁移后伪装成原版本。
- 数据库尚未产生新事实但应用发布失败时，先保持盘点写入口关闭并验证降级前置；只要降级门禁
  拒绝，就采用前向修复。
- 必须回到迁移前状态时，只能在获批事故流程中停止全部写入，恢复迁移前的完整一致性备份，并
  同步恢复匹配的旧应用镜像。不得把单表恢复或部分 schema 降级称为回滚完成。

## 4. 放行证据

正式放行记录至少应包含：Git SHA、镜像摘要、GitHub PostgreSQL 16 release-gate run、迁移前后
revision、备份与恢复演练结果、函数体/ACL 校验结果、维护窗口起止时间、实例清单、隔离 UAT
结果和双人复核人。任何一项缺失都只能记为“尚未放行”，不能用本地测试通过代替。
