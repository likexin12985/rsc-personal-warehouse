### 后续审批封存切片的实现约束（设计，尚未实现）

现行 0146 仅保护原报损提交，0147/0148 的审批原请求各自独立；不能复用 0146 的封存行，也不能把待处置审批当成库存事实。

1. 新增独立审批请求封存事实，明确 `regional/headquarters` 阶段、原报损 ID/type、所属区域、原审批人 user/person、授权版本、原 request ID、带阶段命名空间的 key hash、原命令 hash 和 submission plan hash。原命令原文应按对应严格合同生成规范化 intent 并留存，以便数据库独立重算摘要；总部 intent 包含精确区域核实 ID/hash 及全部逐行决定。不得以客户端声明的 `stock_effect`、审批状态或库存数量作为事实。
2. 封存使用原请求坐标，不生成替代审批请求。优先回查：已存在准确审批返回原结果；已封存准确重放返回原封存；同 ID/key 绑定不同原单/人员/摘要则冲突。查不到结果不自动重发，也不以新的幂等键绕过。
3. 区域/总部封存写入仍须当前对应写权限、本区域或全国范围、申请人不得自审；成功结果回查仅要求当前对应读权限。当前写权限、原审批历史权限和当前读取权限三者不能混用。
4. 新增迁移而不修改 0146/0147/0148 历史迁移。封存插入和原审批插入必须使用相同库存账头锁序；数据库在实际 COMMIT 检查双向互斥，覆盖同 actor/request、同阶段 key、原审批行及其审计/状态/outbox/通知的孤立证据。`READ COMMITTED` 条件、等待后新快照和实际提交期限必须实测，不能仅依赖 Python 的“先查后写”。
5. 原审批人可以是总部或区域人员，原申请人停用不能使既有事实失效。当前审批人停用、范围/授权撤销或到期则拒绝新封存/审批。封存只产生独立不可变封存与审计，不解冻、不调拨、不生成库存交易，也不伪造审批通知。
6. 所有新增证明函数保持迁移角色所有、固定 search_path、API 无直接 EXECUTE，明确 API 表列权限；封存 UPDATE/DELETE/TRUNCATE 拒绝。迁移前置校验及运行期安全目录覆盖来源/hash、触发器、函数 ACL 和形状；SQLite 无等价证明时拒绝此写入。
7. 正式 HTTP 写入口需重检当前人员和请求头，COMMIT 后才返回成功；提交前故障完整回滚，提交回执丢失只回查。区域核实仍为 awaiting_headquarters/stock_effect=none，总部批准仍为 disposition pending/stock_effect=none。

## 2026-09-29 报损审批接口与恢复的前置缺口复核

本轮在 PG16 原生验证期间只读核对现行服务，确认下一业务切片不能只给审批服务增加 POST 路由：

- `stock_loss_recovery.authorize_lookup()` 和 `_original()` 只允许原报损申请人查自己的提交请求，不能直接充当区域或总部审批人的恢复接口。
- `verify_regional_loss()`、`approve_headquarters_loss()` 在寻找同键历史结果之前先要求当前审批写权限。因此，写权限撤销后仍有读权限的审批人，不能靠再次 POST 恢复已提交结果；需独立只读回查并核验不可变审批证据。

- 区域审核必须绑定本区域、原单计划摘要及审核人；总部终审还必须绑定准确区域审核 ID/hash 和每条原明细的处置决定。申请人自审继续禁止。两次审核均为 `stock_effect=none`；终审通过仍为 `disposition_stage=pending`，不等于已经解冻、退回或报废。
- 正式审批待办/详情、回查/封存、当前权限与历史权限边界、HTTP COMMIT 结果未知和客户端恢复应作为同一可验收切片；真实权限种子与业务开通仍需另行核验，不能因内部服务或合成测试通过就宣称已上线。
