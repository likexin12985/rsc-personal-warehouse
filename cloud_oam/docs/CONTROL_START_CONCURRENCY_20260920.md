## 问题与修复

7.62 留下的发布/启动锁顺序差异已在原生 PostgreSQL 16.15 中复现，出现实际 `40P01`。
原新任务启动先锁控制来源，再等待发布者已持有的人员权限图；发布者随后等待控制来源。
启动改为账本 → 人员权限图 → 控制来源后，还复现提交阶段的第二条循环：0100/0101/0103
退回相关触发器对无关发布授权审计先锁账本、再忽略，而启动者已经持有账本、正在等权限图。

本批调整新任务启动锁顺序，并在控制来源等待结束后重新检查当前身份、授权、截止时间、
业务键和完整控制版本。已有任务回读继续沿既有任务/权限图/审计路径处理，不重建任务。

新增前向迁移 `20261102_0123_seal_audit_lock_scope.py`：三项退回校验函数将既有的无关
事件忽略判断移到账本锁之前。退回、取消、出库、库存交易和封存的原有验证正文全部保留；
没有添加角色权限、表或触发器。此前 122 个迁移保持原字节。

迁移先锁住所有调用这三项函数的表，逐个核验准确原文摘要、owner、私有 ACL、函数属性及
审计触发器，再原子替换。readiness 与安全目录推进至 0123。downgrade 只恢复原锁行为，
不删除任何业务事实；继续降至 0121 时，0122 的零库存启动历史保护仍会拒绝且整体回滚。
