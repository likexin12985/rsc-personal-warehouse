# 0164 后报废及失而复得完整实现方案

设计基点：`cb0210da25881d2198a6e31b2195a894e4e74409`。依据正式基线 §1.6、§1.11、§3.9、§3.11、§6。**本文件是待实现设计，不是功能已完成、迁移许可或生产验收。** 旧 2026-09-26 方案仍保存背景，但不能继续沿用其“所有报损尚未实现”的结论。

2026-10-02 实施起点：工作树已增加 `backend/app/stock_scrap_schemas.py`，明确区分原始终审与纠正终审来源，预览/执行/完整原请求回查与封存均使用严格、不可变输入；数量、账户、SN 和权限不能由客户端覆盖。24 项契约测试通过，包括伪造嵌套模型重新校验。**尚无报废持久事实、迁移或写接口，恢复审批及生命周期仍待实现。** 新契约未注册生产路由，不改变既有拒绝规则。

## 1. 业务结果与不可缩减范围

工程师报损冻结后，经区域核实和总部明确批准报废，再由具有当前权限的执行人提交独立报废单。过账将准确数量/SN 从原冻结账户移出可管理资产；批准、报废执行、通知送达是三个不同事实。误报/失而复得通过有独立审批及实物证据的反向单恢复准确原冻结账户，保留报废记录，再由新批准决定后续处置。

必须支持数量和 SN、带批次维度、原始报损处置与后续纠正处置、多代报废/恢复历史。报废后仍为原保管人/原资产所有组织保留追溯；不得创建“scrapped 可用余额”冒充资产移出。若实际责任已变更，应进入明确交接/异常处理，不能借用其他账户补足。

## 2. 当前阻断点

- `stock_loss_planning.plan_dispositions` 已能生成 `stock_operation_scrap` 外边界计划，但纯计划不具备写权限。
- `StockOperationOrder` 仅允许 return/loss_report；`StockOperationLine` 目前假定有不同的库存账户和 reserved 账户。报废外边界没有目标账户，不能伪造目标或工单。
- `StockLossDisposition` 只允许三种账户处置及派生退回，`target_account_id` 非空。纠正执行也只有恢复/旧/坏。需要显式报废分支和非空/空值组合约束，避免 SQL NULL 三值逻辑绕过。
- `inventory_posting` 和 `serial_ledger` 都拒绝 SN scrap。PG 的 SN 生命周期与原处置守卫也必须同步扩展；仅改单个 Python 分支不会形成合法业务链。
- 现有反向准备从 `execution.target_account_id` 取得来源，要求 active SN。报废恢复来源是受控外边界，当前 SN 应为 scrapped；必须新增精确原报废证明，不能复用空账户绕过。
- HTTP 预览/结果、请求恢复/封存、执行来源、历史链、前端只有现有分支；必须同批覆盖。

## 3. 持久事实与迁移策略

采用前向迁移，不修改 0158–0164 已冻结 SQL 的业务含义，不回填或覆盖已过账历史。新 revision 编号在实施时根据真实单 head 确定。

1. 沿用基线共用库存作业单头，增加独立 scrap 类型。用准确终审决定或纠正决定关联到唯一原报损行，来源必须互斥且有真实 FK；不伪造退回路线/工单。单头继续承载单号、操作者、请求、原因及对应原子过账。原 return/loss_report CHECK 的全部必填和证明保持不变。
2. 新增报废专用逐行事实，绑定共用单头、批准来源、原冻结行、准确账户/数量/SN、posting transaction/movement。使用专用行避免把旧 `StockOperationLine.reserved_account_id` 硬解释为不存在的外边界目标。共用单头的一对一/逐行覆盖由 deferred proof 约束。
3. 原始处置及纠正执行新增准确 scrap 单关联；只有 scrap 分支允许 target_account_id 为空，其他分支仍要求真实不同目标；禁止同时带 return 与 scrap 关联。新事实/原决定/原冻结份额/流水必须相互吻合，未知类型拒绝。
4. 新增独立恢复申请与区域/总部审批事实，绑定准确原报废执行、实物证据及数量/SN；申请人不得自批。执行恢复时追加专用反向单和严格逆流水，恢复到原冻结账户，随后进入现有新批准流程。不能用旧的报废批准反向推导“恢复已获批准”。
5. 请求执行/封存保持原操作者、请求号、幂等键、请求 hash、计划 hash 和全局唯一绑定。不存在与永久关闭分别表示；同键不同内容拒绝，封存/执行竞争只允许一方提交。
6. 迁移逐项核验前驱函数、属主、ACL、触发器及约束；对存量表逐行摘要前后比较。空库往返可以恢复原 schema；存在新报废/恢复/封存事实时降级必须拒绝，保留 head 与全部事实。不得删除新历史使降级成功。

## 4. 原子执行和生命周期

预览先核验当前主体权限/作用域、原完整报损历史及终审、共享冻结账户中本行份额、当前期初/策略/保管关系、数量精度与准确 SN。生成服务器计划 hash。执行锁顺序遵循现有库存头和主体图规则，在锁内重读，不能信任客户端的任意计划 JSON。

报废流水为 `frozen → 受控 stock_operation_scrap 外边界`，库存资产减少准确量；SN active→scrapped，当前位置为空，原所有组织、最后 movement、原 admission 仍由不可变历史重建。报废业务单、流水、余额/SN 投影、独立审计/状态/通知事件在一个事务内提交。

恢复流水必须严格反向到同一个冻结账户并引用原交易，SN 的最后活动必须就是被恢复的报废，不允许移动后倒冲旧事实。由原报废之前的不可变历史恢复生命周期，不能信任被手工改写的当前缓存。恢复之后仍冻结，不能自动可用、自动入他人个人仓或自动关闭原单。

Python 写入校验、Python 历史重建和 PG COMMIT 约束必须共用相同业务定义，分别拒绝伪造来源。普通 `post_inventory_transaction`/通用 reversal 不得成为绕过专用父单的入口。新私有函数无 API 直接 EXECUTE；既有认证/授权审计仍保持 0164 的锁范围。

## 5. API 与客户端

- 总部执行页为 scrap 显示独立报废预览/单号/执行结果；显示批准与实物执行两条状态。原始与纠正来源均可进入，不能只把枚举放进下拉框。
- 私有 `/xx` 支持恢复申请、实物证据、当前原报废/SN 核对；区域和总部独立复核，执行人看到明确授权结果。公开首页和公开小程序范围不变。
- 每个写动作保留完整原请求及原身份版本；响应丢失后精确 lookup，不自动发新键。回查输出不能泄漏内部证据/请求或他人权限信息。
- 详情并列显示原报损、冻结、批准、报废、恢复批准、反向和后续纠正；通知失败只进入独立送达异常。任务中心须显示待审批/待执行/结果待确认。

| 数量/SN × 原始/纠正报废，含批次 | 当前批准与本行冻结量准确，真实 API 角色 COMMIT；资产仅减少批准报废量，其他冻结单不受影响 |
