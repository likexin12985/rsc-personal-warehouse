# 报损派生退回补偿：实现边界与下一批开发

2026-10-01，根据正式基线1.6、1.8、1.11、2.3、3.5、3.11及第6节，核对当前0161代码。本文是后续实现设计，不是已完成的补偿接口或上线验收。原退回收货、独立入库、原请求恢复已有实现；缺口是它们之后的纠正与逆向业务。

本轮已新增`return_history.py`和`return_progress.py`：内部只读核验原处置、各履约事实、精确关联、当前总部读权限、游标及快照，再给出互斥数量/SN份额。29项本地测试通过，数量/SN原生权限核验仍在独立副本运行；未开放公共接口或补偿写入。原`return_dependencies.read`仍只是依赖ID，不能用它替代新图的完整证明。

**新增前置缺口：破损接受量错误入新件可用库存。** 数量/SN均已用真实合成服务复现，详见[破损入库修复范围](RETURN_DAMAGED_INBOUND_GAP_20261001.md)。历史图能如实指出既有事实，但不能把错误分类当作正确业务；应先完成该修复再实现逆向补偿。

## 已核对的实际边界

- `stock_loss_return_commands.execute_loss_return`生成总部批准对应的派生退回，并把原个人仓冻结库存转至同人的待退回账户。该步骤没有发运、验收或区域入库。
- `stock_return_origins.verify_return_origin`显式区分工单退回和报损派生退回。报损退回没有OAM工单引用；总部执行人与实际发件工程师可以不同，不能用创建人替代当前保管责任人。
- `stock_return_commands.cancel_return`只实现普通退回整单取消，要求创建人及申请人均是当前用户，并调用普通退回历史证明。报损派生子单不能直接套用该入口；已有出库时也禁止整单取消。
- `stock_return_outbound_plan.departed`从准确出库事实累计数量/SN；实物出库把待退回库存移至在途账户。发运是另一个事实，不再重复减少库存。
- `stock_return_receipt_commands.execute_receipt`只记录验收，正常、破损、拒收、短少分开；不会凭验收成功直接生成入库交易。
- `stock_return_inbound_commands.execute_return_inbound`要求准确验收和当前接收责任人，独立将接受数量从在途移到区域库存。当前每份验收只能有一份入库事实。
- `stock_loss_corrections.return_dependencies.read`只给出原子单五类下游ID，虽复读游标和审计头，但不证明这些下游事实完整有效，也不证明补偿已完成。不能直接据此解锁写入。
- `reversal_stock._return_boundary`拒绝越过任一下游事实；`inverse_posting.execute_account_inverse`还明确拒绝退回/报废。来源GET返回`dedicated_compensation_required`。这些限制必须保留到完整业务和数据库证明可用。
- `return_posting_facts._verify_child`目前把原派生退回的取消记录视为历史不一致。增加补偿时须区分“原始事实真实”与“当前是否可继续履约”，不能删掉历史校验或让旧请求恢复依赖今日状态。

## 按实际阶段处理，不用最高状态覆盖整单

一张单可部分出库、多包裹、分批验收和入库，因此同一明细可同时处于下面多行。处理对象必须绑定原处置、子单、明细、出库行、包裹行、验收行及入库行；SN逐件分区。

| 已发生事实 | 补偿要求 | 库存边界 |
| --- | --- | --- |
| 仅派生退回，尚未出库 | 证明全量仍属原人待退回，独立登记停止子单履约及原处置冲销 | 待退回→原冻结账户；不能直接恢复可用或同时批准下一次处置 |
| 部分实物出库，尚有未发出数量 | 未发出部分与已发出部分分别处理，禁止套用普通整单取消 | 未发出部分保留准确份额；已发出部分需真实交回证据后才可离开在途 |
| 已发运，未验收或存在拒收/短少 | 原运单、物流与异常事实保留；另登记退运/找回、实际交接和验收 | 发运撤销或物流签收不证明实物回到个人仓；短少不能自动补成库存 |
| 已验收，未区域入库 | 补偿必须由当前接收责任人处理，阻止该份额被并发正常入库 | 验收修正本身不改变库存；实物返还仍需后续独立移动 |
| 已区域入库 | 从准确入库行证明后续未消耗/转移份额及当前SN位置，关联逆向出库、退运、回收验收 | 不得从区域账户直接“瞬移”至个人仓；库存随实际保管和位置变化过账 |
| SN有后续使用、再调拨、报废或责任人交接 | 沿原SN/后续流水继续处理；不得选择同SKU其他SN抵偿 | 未证明可回收前，不允许回到原冻结账户或开始新的纠正处置 |

## 需要新增的事实与不变量

以下为待实现模型职责，名称未冻结，不得把它们当作现有数据库表：

1. 补偿单绑定准确原处置及退回子单、原始请求摘要、申请理由和证据；总部批准与实际执行分别追加。审批不移动库存。申请人不能自批。
2. 补偿行绑定原业务行及份额，分别保存停止原履约、实际逆向交接、逆向发运、验收、入账引用。每阶段使用独立权限、请求ID和幂等键。
3. 停止原履约必须与并发出库/发运/验收/入库争用同一业务份额；只关闭仍未发生的未来动作，不能删除已发生的事实。
4. 数量用`numeric(18,3)`；正常履约已消费份额与补偿占用份额总和不能超过原行数量。拒收、短少、破损分别守恒；破损作为接受数量的分类不能再加一次。
5. SN必须属于准确原行；同一SN不能同时进入正常履约与补偿。保管责任、位置、成色、可用状态均独立验证。
6. 原流水保持不可变，新库存动作走统一原子过账入口，业务事实、审计、通知Outbox在同一事务提交。数据库提交时再次验证权限、原请求绑定及份额，不能只依赖Python预检。
7. 所有相关份额补偿完成且重新证明原冻结库存后，才允许关闭该轮原处置执行、进入独立纠正审批。未完成份额不能被整单状态掩盖。
8. 原报损/退回/收货/入库请求永远恢复原提交结果；新补偿请求单独保存、只读查询、显式永久封存。超时或`not_found`不自动重发。

## 实施顺序与完成证据

先补完整只读履约事实图及逐行数量/SN分区，将历史真实性与当前操作资格分离；随后实现未出库补偿及当前履约并发隔离，再实现有下游事实的逐阶段逆向物流。最后接入H5的预览、明确确认、单次发送和原请求恢复。未出库路径通过不能作为下游补偿完成。

后续新增迁移须从实际单head衔接，冻结支持目录并保留0161历史；不得修改旧迁移“顺便兼容”新补偿。每个阶段须证明：数量和SN真实PG16提交、部分履约、跨包裹累计守恒、不同角色、撤权后拒绝、并发正常履约/补偿单一赢家、响应丢失恢复、原历史恢复、恶意绕过Python后的数据库拒绝、有历史拒绝降级、最小权限和正常停库。

正式完成仍需真实多角色终端验收、实际返还证据及迁移演练，不能由合成测试或本设计替代。
