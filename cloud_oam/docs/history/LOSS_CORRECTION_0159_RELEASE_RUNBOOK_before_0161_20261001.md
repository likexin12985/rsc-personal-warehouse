## 迁移和角色

- 前置版本 `20261207_0158`，目标版本 `20261208_0159`。迁移支持目录随版本文件一起打包，不依赖开发 artifacts 或运行时 ORM 生成 DDL。
- 5 个新增表包括冲销、独立纠正批准、纠正执行、逆向请求封存和数据库请求键绑定。API 只对前 4 个事实表具有 SELECT/INSERT；绑定表只读，通过一个受控函数登记。既有不可修改约束、延期提交校验与库存权限继续有效。
- 应用启动检查表、约束、函数正文、触发器及权限。未知或漂移状态应停止启动，不能直接放宽权限消除错误。
- 业务 RBAC 配置是独立发布项。测试中的合成角色授权不证明真实人员具备正确权限。
- 0159及后继0160的角色、函数目录、权限与历史检查依赖真实在线查询；不得用 `alembic --sql` 生成物代替正式迁移或跳过预检。生产 `env.py` 已要求在线迁移。当前本地离线入口诊断修复的候选及状态见 `CONTINUE_DEVELOPMENT.md`，候选验证不代表已应用主树。

## 独立 DBA 引导

0159 使用位于私有模式 `rsc_loss_uuid_0159` 的 `uuid-ossp` 1.1 扩展，由独立 `postgres` DBA 安装。迁移角色不能安装本机 C 函数；API 不获得私有模式 USAGE 或 UUID 函数 EXECUTE。

新建 Docker 数据卷时，现有 `10-create-application-roles.sh` 先创建应用角色，随后自动执行 `deployment/postgres-init/20-loss-uuid.sql`。现有数据卷不会重跑初始化目录；重启容器不能替代引导。发布前需在已核对身份、备份和目标数据库的部署会话中，以独立 DBA 对目标应用数据库执行同一 SQL 文件，之后才由 `star_oam_migrator` 执行 Alembic。禁止把管理员连接串用于 API 或 Alembic。

引导要求 PG16、明确的非系统应用数据库、数据库由迁移角色拥有、DBA 为 `postgres` 且应用角色无超级权限。整个引导为单一事务块；完全相同的重复执行只检查目录。扩展已安装在其他模式、安装不完整、函数或权限不符时直接拒绝，不能自动移动扩展、撤销未知授权或覆盖函数。错误必须保留并人工审阅。

## 本地与 CI 门禁

在 `cloud_oam` 运行下列入口，`--postgres-bin` 必须指向已校验的本机 PG16 bin 目录：

```sh
.venv/bin/python scripts/run_local_pg16_loss_correction_checks.py \
  --postgres-bin /absolute/path/to/postgresql16/bin \
  --correction-kind restore_available
```

默认分别创建数量和 SN 两个全新私有 Unix socket 数据库；另分别运行 `convert_used`、`convert_damaged`。不接受既有 DSN、服务器或数据目录。每次保留源码摘要、升级/降级日志、业务检查和停库回执；进程退出及日志中的单项 PASS 不能代替 `terminal-v1.json`、无源码漂移和正常停库。

门禁实际执行全版本升级、0159 空表降回 0158 并重升、完整 API 启动校验、真实期初与报损/批准/处置、冲销、独立纠正批准、纠正入账、封存、只读请求恢复和拒绝场景。有历史再降级必须被拒绝，且仍停留在 0159。纠正业务使用迁移授予的数据库权限，不得临时 GRANT 使其通过。

CI 的 `pg16_loss` 矩阵增加 `correction_restore`、`correction_used`、`correction_damaged`，各含 quantity/serial。沿用真实 GitHub 托管、全新 PG16 和显式可销毁数据库确认边界。调度单元测试只证明分支路由与错误传播；本地 PG16 通过也不等于当前提交 SHA 的 GitHub 门禁通过。

## 保留历史与回退

空表降级仅用于已确认无业务历史的测试或受审环境。任一新增事实或已有 `stock_loss_dispositions` 存在记录时，0159 拒绝降级；它可能先于旧版本的历史保留检查返回错误。因此旧流程在当前 HEAD 的门禁必须核验最高版本的拒绝结果，并确认目录、业务事实与版本号没有变化。

不得通过删除事实、修改版本号、关闭约束或盲目重放请求来降级。生产回退需要独立证明兼容性或恢复方案；本说明不授权生产迁移、数据恢复或业务写入。
