## 独立 DBA 引导

0159 使用位于私有模式 `rsc_loss_uuid_0159` 的 `uuid-ossp` 1.1 扩展，由独立 `postgres` DBA 安装。迁移角色不能安装本机 C 函数；API 不获得私有模式 USAGE 或 UUID 函数 EXECUTE。

新建 Docker 数据卷时，现有 `10-create-application-roles.sh` 先创建应用角色，随后自动执行 `deployment/postgres-init/20-loss-uuid.sql`。现有数据卷不会重跑初始化目录；重启容器不能替代引导。发布前需在已核对身份、备份和目标数据库的部署会话中，以独立 DBA 对目标应用数据库执行同一 SQL 文件，之后才由 `star_oam_migrator` 执行 Alembic。禁止把管理员连接串用于 API 或 Alembic。

引导要求 PG16、明确的非系统应用数据库、数据库由迁移角色拥有、DBA 为 `postgres` 且应用角色无超级权限。整个引导为单一事务块；完全相同的重复执行只检查目录。扩展已安装在其他模式、安装不完整、函数或权限不符时直接拒绝，不能自动移动扩展、撤销未知授权或覆盖函数。错误必须保留并人工审阅。

## 本地与 CI 门禁

在 `cloud_oam` 运行下列入口，`--postgres-bin` 必须指向已校验的本机 PG16 bin 目录：

```sh
.venv/bin/python scripts/run_local_pg16_loss_correction_checks.py \
  --postgres-bin /absolute/path/to/postgresql16/bin \
  --correction-kind restore_available
```

默认分别创建数量和 SN 两个全新私有 Unix socket 数据库；另分别运行 `convert_used`、`convert_damaged`。不接受既有 DSN、服务器或数据目录。每次保留源码摘要、升级/降级日志、业务检查和停库回执；进程退出及日志中的单项 PASS 不能代替 `terminal-v1.json`、无源码漂移和正常停库。

当前门禁执行全版本升级、空表降回0158并重升当前head、完整API启动校验、真实期初与报损/批准/处置、冲销、独立纠正批准、纠正入账、封存、只读请求恢复和拒绝场景。含0161请求绑定历史的降级必须在0161被拒绝，仍停留于0161。纠正业务使用迁移授予的数据库权限，不得临时GRANT使其通过。

CI的`pg16_loss`保留已有全部分支，包括三种纠正处置、多代历史和逆向封存历史；另增加`correction_request_seals`、`correction_http_sources`，均含quantity/serial。两个新增场景的本地入口为：

```sh
.venv/bin/python scripts/run_local_pg16_loss_correction_request_checks.py \
  --postgres-bin /absolute/path/to/postgresql16/bin --scenario seals
.venv/bin/python scripts/run_local_pg16_loss_correction_request_checks.py \
  --postgres-bin /absolute/path/to/postgresql16/bin --scenario http_sources
```

两个新增场景分别验证独立批准/执行封存，以及注册HTTP来源、预览、写入和原请求恢复。数据库事务/角色真实，登录主体是合成身份，不覆盖生产JWT/短信渠道。空库往返允许合法重建函数导致内部OID改变，但业务数据、函数定义/安全属性/权限、触发器必须相同；拒绝历史降级继续检查既定不可变事实。不能为了通过测试而放宽业务约束。

CI沿用真实GitHub托管、全新PG16和显式可销毁数据库确认边界。调度单元测试只证明分支路由与错误传播；本地PG16通过也不等于准确提交SHA的GitHub门禁通过。此处列出入口，不宣称所有分支已经通过；运行状态见开发接续。

## 保留历史与回退

空表降级仅用于已确认无业务历史的测试或受审环境。0161存在纠正请求历史时先拒绝降级；没有此类历史也不表示可随意回退，0159仍会拒绝删除已有处置等业务历史。因此门禁必须按本场景实际保留的历史核对拒绝版本，并确认目录、业务事实与版本号没有变化。
