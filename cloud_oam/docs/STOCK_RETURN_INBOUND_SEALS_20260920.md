## 已实现

- 新增 `stock_operation_return_inbound_seals`，保存准确 receipt、shipment、当前操作者与授权
  版本、原 request/hash/reference、时间。一个操作者的请求只能绑定一个封存事实。历史
  `StockOperationCommandSeal.receive_return` 仍表示包裹验收封存，不推断对应哪次入账，不迁移
  或改写历史记录。仅存旧封存审计但原事实缺失时保留结果未知，不创建替代入账封存。
- 入账封存与实际入账使用同一库存总账锁；去掉 API 对不可变验收表的直接 `FOR UPDATE`，
  不为锁定而扩大 API UPDATE 权限。服务拒绝封存后迟到提交、换 key 重发和跨验收单回查。
  同一包裹的两次验收各自封存后，仍可明确使用各自的新请求完成独立入账。
- 新封存用自己的不可变审计类型和正文；GET 验证原验收、精确请求与封存审计链、当前读权限、
  库存/审计快照及不存在执行证据。GET 使用 `no_autoflush`，不会提交调用方待写 Outbox。
  已完成入账的封存回查继续返回原入账结果，封存本身不改变库存或验收状态。
- 后端返回 `{schema_version, lookup_status, seal:{...}}`，真实 HTTP 新封存结果已交给现有
  小程序解析器验证；重复封存返回同一事实，摘要冲突拒绝。旧验收封存不会冒充入账封存。
- 既有提交、取消、出库、发运和验收的请求占用/恢复检查同步纳入入账事实及新封存，防止
  同一操作者的 request 在不同退回操作之间重复使用。

## 前向迁移与数据库门禁

0110 增加一个表和一个守卫函数，使用 12 个触发器接入事实、审计和库存状态事件。PostgreSQL
提交时在总账锁内验证八类退回请求互斥、准确验收归属、当前接收权限、完整封存审计及不存在
迟到执行证据；约束触发器为 `DEFERRABLE INITIALLY DEFERRED` 且 `ENABLE ALWAYS`。
为了确保等待总账锁后读取新提交事实，该提交约束只接受 `READ COMMITTED`，其他隔离级别拒绝。

API 对新表只有 SELECT/INSERT；不可 UPDATE/DELETE/TRUNCATE，守卫函数只由 owner 的触发器
调用。已有新封存拒绝降级。升级发现 0109 时代入账与旧请求冲突时直接阻断，不重写历史记录。
SQLite 仅实现新表不可变和跨表请求冲突，不能替代 PostgreSQL 延迟审计与并发证明。

readiness 从 0109 的 `8422e512…1ead52` 精确推进到 0110 的 `2e5527dd…34b935`；测试从原始
readiness SQL 重建并验证两个完整 SHA256。正式安全清单纳入新表、函数、触发器及 `_0110`
