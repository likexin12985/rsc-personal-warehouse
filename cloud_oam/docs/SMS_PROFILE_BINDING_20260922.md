2026-09-22，固定 `06f6/oam` 工作树，分支 `codex/notification-delivery-worker`。没有新迁移、真实短信、供应商请求、提交或部署；Alembic HEAD 保持 `20261113_0134`。

## 问题与修复

发送准备时已保存请求摘要，但正式校验此前只查手机号、供应商和客户端，随后使用当前配置调用 PNVS。部署中切换方案时，旧验证码可能在新方案校验。阿里云 [CheckSmsVerifyCode 官方契约](https://help.aliyun.com/zh/pnvs/developer-reference/api-dypnsapi-2017-05-25-checksmsverifycode)要求校验方案与发送一致；2026-09-22 已重新核对。

现在以即将调用的同一个供应商实例及其配置副本生成摘要，在数据库准确挑战/投递锁内，与发送时 `request_sha256` 按原算法重建比对：`SHA256(formal-sms-dispatch-request-v1|challenge_id|profile)`。摘要包含手机号 hash、方案、签名、模板、长度、有效期、间隔及重试策略，不包含验证码或凭据。缺失、格式异常和配置不匹配均停止，不能回退到另一份全局配置。

- 校验前配置不符返回固定 503 原因，不增加验证码错误次数、不消费挑战、不创建新会话；原配置恢复后可继续准确旧挑战。
- 延迟发送前同样核验；配置不符时本次 worker 不调用供应商，保留 `uncertain` 和 `provider_configuration_changed` 原因。不能换键、释放原投递权或自动补发。
- `local_hash`、`legacy_unknown` 历史模式不能取得当前 PNVS 的验证授权。`begin_verify`、`finish_verify`、`consume_verified` 包括状态回放均在变动前拒绝，保留旧数据。既有 HTTP 幂等响应恢复独立处理，不把历史验证码重新认证成新会话。
- 供应商返回 `PASS`、身份准入、挑战消费、会话建立仍为各自的事实；通知、审批和库存不受影响。

同一云账户的凭据轮换不改变短信请求摘要；跨账户切换不能据此视为同一方案，应先停发并处理存量挑战。专用 STS/云角色隔离、费用/设备限频、可信回执及真实账号联调仍在 PNVS-01 范围内，本次未关闭这些缺口。
