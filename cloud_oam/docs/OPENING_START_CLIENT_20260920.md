# 按发布批次启动期初盘点与客户端恢复（7.70）

本批把已有服务端启动和结果查询接口接入网页及小程序私有页面。默认启动开关仍关闭，
公开网站和个人主体小程序仍为“交流备件知识大全”，星星管理入口保持 `/xx`。
这批交付是可验证的候选代码，未启用业务、提交、推送或部署。

## 已实现

- 使用已有四层目录选择区域、资产归属、实际仓位和执行人，再选择已发布控制批次。
  可添加多个不重复的资产归属/仓位范围，分别选择整范围冻结或截止流水回算；任务编号、
  盲盘/明盘、截止时间和备注均显式提交。控制数量与来源事实由服务端绑定。
- 首次 POST 前重新读取本人、当前权限、每个选定目录及批次；实际用户 ID 不用人员 UUID
  代替。Web 使用无自动重放传输，小程序使用 `noRefresh`，只发送一次原 POST。
- 持久记录只含协议版本、区域、发布批次、本人、历史授权版本和请求追踪号。不保存请求
  正文、备注、盘点数量、幂等键或凭证。写入后逐字段回读，失败则不发送。
- 一个区域的租约覆盖预检、保存、发送和回查。网页使用浏览器 Web Locks 协调同源标签；
  小程序使用同一服务上下文共享锁。两者均不排队产生第二次新提交，不声称跨设备互斥。
- 原请求未知时，刷新、返回或再次点击只查原结果。成功需要两次一致的历史结果、一次
  严格任务详情及夹在其间的当前验权，才清理准确对应的记录并允许打开任务。
  另一人员、较旧授权、页面隐藏/卸载、详情漂移或损坏记录均不能清理或换键重发。
- 同一人授权版本更新后可在重新取得有效当前权限时读自己的历史结果；历史版本本身
  不授予权限。后端补充测试验证新版本可恢复、旧 principal 拒绝；该新增用例使用 SQLite
  历史事实样本，实际发布能力与数据库约束仍以此前原生 PG16 证据为准。
- 仅首次 POST 的明确 `control_publication_not_admissible` 412 拒绝，可在重新验权后
  清理准确记录。通用 4xx/5xx、网络错误、后来 GET 的相同错误以及 `not_observed` 均不清理。

核心协议位于 `frontend/src/openingStartCore.ts`，通过固定 Node 24.19.0 的
`scripts/sync_opening_start_core.mjs` 生成小程序副本。客户端 CI 增加 `--check`，拒绝
两端副本漂移；工作流结构测试继续严格限制每一步命令和权限，没有放宽原门禁。

## 启用前仍须解决

1. **原请求长期未知时的终结证明。** `not_observed` 只能说明本次未观察到，不能证明
   延迟请求永远不执行。当前保留记录并阻止该区域新启动，没有“丢弃/重试”按钮。下一批
   应沿用正式命令终结模式，设计服务端原请求终结事实及真实并发验证，支持先到的已启动
   结果优先、未执行的准确原请求永久拒绝，不靠删除本地记录解决。
2. **当前候选完整门禁。** 新源码需重新固定后跑 GitHub PG16 完整门禁及客户端 CI。
   既有候选提交例外仍待批，不因此自行提交或上传。禁止本地运行破坏性完整门禁，局部
   数据库实验仅用新建自有 PG16 集群。
3. **真实上线验收。** 真实知识资料导入及审核、控制来源绑定和持续发布最小权限、密钥
   生命周期、实库迁移、三天对账、通知供应商/回调、真机多角色、PITR、负载与灰度仍待。
   多范围/SN/周期盘点及中断完整联调不由本批组件与历史事实样本替代。

启动功能 `OPENING_START_ENABLED` 在两端均为 false。恢复查询可独立使用；保留的小程序
业务页面仍未注册，并显式从公开打包排除。开启开关不得替代上述验收。
