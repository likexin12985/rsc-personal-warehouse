## 已确认的问题和修复

全新私有 Unix socket PG16.15 实例中，备份角色初始没有角色成员关系，目标表有两行，
专用 SELECT 策略允许完整读取；另一个无关角色拥有限制性 SELECT 策略。
原入口预检与快照创建完成后，管理员给备份角色加入该无关角色，不需要等待表上的
ACCESS SHARE 锁。`pg_dump` 和外层归档仍退出 0，但归档中两行均丢失，旧检查没有拒绝。
控制组在成员关系变化前导出两行，反例过程和不完整测试备份包已完整保留。

[PG16 角色成员文档](https://www.postgresql.org/docs/16/role-membership.html)说明了成员关系和
继承规则；本项目的缺行结论来自上述实际数据库反例，未用文档推测代替执行证据。

正式入口现在增加两道防护：

- `policies.sql` 对全部启用 RLS 的 public 表检查所有 SELECT/ALL 限制性策略，不再只看
  当下对备份角色适用的策略。存在任何此类限制性策略就拒绝备份，避免成员关系变化后
  才激活过滤。已有专用完整读取策略检查仍保留，未增加数据库权限或关闭 RLS。
- `lock.sql` 在导出子进程成功后、释放表锁前，用 READ COMMITTED 再执行完整角色/权限
  预检。持续存在的成员关系、建库权限和授权转授权限变化会阻止完成包发布。

此改动会让未来新增的、仅适用于业务角色的限制性读取策略也阻断备份，需要在设计该类
策略时重新审查备份方式。当前 0128 应用结构没有这种冲突，已用完整应用数据验证。
最终复查不是对集群角色 DDL 的锁；不能宣称覆盖任意瞬时角色修改、管理员重命名/重建、
宿主断连或容器故障。角色维护与备份仍须协调，完整生产并发运维验收继续开放。
