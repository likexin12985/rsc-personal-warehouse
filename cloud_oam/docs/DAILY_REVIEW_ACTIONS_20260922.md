## 问题与最终行为

原页面按角色显示审核操作，因此曾解释过对账的人在取得总部角色后仍可能看到批准/退回按钮；总部也可能选择尚未解释或已经退回的差异，直到提交时才被后端拒绝。

当前详情响应增加 `allowed_actions` 和 `action_context`（当前人员、授权版本）。服务端直接复用正式提交的授权函数，检查全局 deny、同一 assignment 的读取/动作权限、有效期、精确区域和唯一匹配授权。查询从同一 SQL 快照读取历史解释人是否包含当前人、是否存在可退回差异这两个标量，不输出历史作者列表或整个内部状态；读取前后重查当前身份与权限，并核对审核版本。

| 档案状态 | 区域人员 | 独立总部审核人 |
| --- | --- | --- |
| 尚未开启 | 有权时开启 | 有权时开启 |
| 已开启、没有解释 | 解释差异 | 暂无审核操作 |
| 部分解释 | 继续解释 | 可退回已解释且尚未退回的项；不能批准 |
| 全部解释齐全 | 可修订解释 | 可批准或定向退回 |
| 已退回 | 补充解释与证据 | 仅可退回其他当前可退回项 |
| 已批准 | 只读 | 只读 |

上述动作均以当前具体授权为前提；数量一致且无差异的档案无需解释，开启后由独立总部审核。曾参与任何一次解释的人始终不能批准/退回，即使当前每项解释后来被别人替换。

客户端必须同时满足服务端动作提示、人员/授权版本绑定以及既有角色和范围检查。缺少动作字段、身份不符、旧授权或不可能的状态组合时停止新提交。退回选择含未解释、已退回或不再有差异的项时整次阻断，不自动缩小成部分提交；支持清空本页选择后重选。无新操作权限时仍保留原请求查询/终结入口及其服务端复核，草稿和待核验记录不被顺手清除。

这些提示只改善操作入口，不能替代写端的当前权限、独立审核、版本、附件可用性和提交时校验。只读响应不授权库存变更，审核通过继续保留原数量差异。

## 原始失败与限制

第一轮全量前端于 21:36:07 开始，组件及对应测试在 21:36:22 仍有修改，出现 **1,376 passed / 3 failed**，均为新测试找不到旧组件中的“清空本页选择”。该轮不能作为准确候选通过；原始 `frontend-full.log` 保留。停止修改并冻结 224 个输入后，完整复跑通过。后端最初一次探针漏设 `PYTHONPATH` 只在 collection 阶段失败，修正环境后的聚焦结果才作为通过证据。

首轮真实 PG16 运行在 9 次动作 GET 通过后，因测试为区域所属人员添加全国总部角色而失败，实例已停止，原证据保存在 `artifacts/daily-action-capabilities-pg16-20260922/`。正式规则要求总部角色对应总部所属人员，因此只修正合成夹具：在第二轮夹具准备完成、任何审核开始前，将该合成人员绑定总部组织并保留明确区域授权；不放宽生产授权校验、不修改已有实例或重用数据目录。

新动作查询测试进入 PostgreSQL 16 静态 CI 清单，真实动作读取断言进入共享 PG16 runtime；远端 CI 尚未运行。浏览器 HTTPS 附件上传到总部独立审核的完整链路、多设备/跨标签现场验收、真实 OSS/身份、当前八角色容器联合恢复及连续三天真实对账仍缺。

发布时先部署兼容的 API，再更新私有前端。新字段对旧前端是附加信息；新前端连接缺少动作字段的旧 API 会拒绝详情核验和新提交，不能把这种失败当作“没有差异”。
