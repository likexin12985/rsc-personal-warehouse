## 修复的具体问题

1. 旧查询重用写服务的“冻结必须 active、全部初盘执行人今天仍有效”条件。
   合成数据通过真实三轮、两级复核、过账和关闭服务复现：approved 可读，posted/closed 复盘 503。
2. 新内部 `CountHistoryContext` 绑定当前 Session/事务、任务、目标操作/轮次/范围及祖先轮集合，
   保存已重证的范围计划和已预锁文件全集。它不是 HTTP 参数、写操作许可或跳过校验开关。
3. 历史来源使用创建事件、范围 key/hash/manifest 和截止快照；不要求无关旧执行人今天仍在职。
   当前 caller、授权版本、目标范围及保管关系仍按当前数据库时间校验，文件等待后和返回前重验。
4. released 冻结只在完整唯一的过账 completion、有效审批范围/轮次、释放时间/操作者/固定原因、
   approved→posted 事件与审计都能重证时成立；全部历史实盘必须早于或等于释放时点。
   复用的是纯有效审批证据算法，不伪装旧时间或任务状态，不调用要求当前恰为 posted 的重放入口。
   该证明仅确认历史计数发生在合法冻结区间，不对外提供库存过账/关闭完成回执。
5. 来源对象保留 `ancestor_graph`，递归重证初盘及每层复盘的计数、差异、复核、案例与审计。
   文件全集在递归前取得；来源 manifest 使用上下文中的预锁文件，不先锁祖先子集再补全集。
6. 所有普通写服务默认 `history=None`，继续要求当前人员资格、活动冻结和原状态机；未放宽写入条件。
   不存在 trace 仍只能返回 `not_observed`，不能清除哨兵、换幂等键或自动重放。

## 回归范围

合成 SQLite 检查：

- 三轮 approved/posted/closed，各原 trace 与未见 trace；全映射表行值、事务与 SQL 只读。
- 缺 completion、错误释放原因/操作者/时刻、过账摘要、状态事件或审计损坏均失败关闭。
- 当前目标权限撤回、授权版本变化、保管变更仍拒绝；祖先计数审计损坏仍拒绝。
- 双初盘范围、仅一范围复盘：无关工程师离职、账号停用或保管变更不牵连合法历史查询。
- 原写侧来源校验未传历史上下文时仍拒绝失效事实。
- 上下文跨 Session/事务/坐标、错误封印、未知文件及字段修改拒绝。
- 三个真实附件按祖先逆 UUID 顺序建立，实际应用 SQL 只有一次全文件集合行锁。

一次性 PG16 门禁新增内容（以最终运行结果为准）：

- 真 API 角色与正式业务服务，每步独立提交；初盘→两次复盘→区域/总部复核→实际 +1 盘盈过账→
  独立对账→关闭。仅过账改变库存；每个 GET 前后持久行值完全一致。
- 两份跨轮逆 UUID 合成附件，不连接 OSS；各阶段三轮原 trace/未见 trace HTTP 回查。
- 错轮次 404、错操作 400、错身份/版本 412、隐私头、调用方事务与全行只读检查。
- 0062 升级/降级/再升级目录、readiness 身份及 SHA；API 直接锁只读表仍拒绝。
- ledger holder 阻塞 owner 时任务行未被提前锁定；owner 获锁后祖先、终态、账户、人员及全部文件
  的另一事务 NOWAIT 争抢均阻断。查询和竞争验证不写业务事实。
