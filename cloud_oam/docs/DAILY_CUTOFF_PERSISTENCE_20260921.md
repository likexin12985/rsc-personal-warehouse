## 新增的不可变事实

`daily_reconciliation_cutoffs` 固定来源发布批次、映射批准记录、上海业务日期、账本游标、
两侧原始采集时间、完整快照、计算结果、操作者/原会话和授权审计。请求只含批次及映射的
ID/摘要、日期、幂等键和请求号，不能上传原始库存 JSON 或指定数量。

当前内部候选要求真实有效的总部 Web 会话、授权版本和 `inventory_control.authorize`。
新截止要求来源采集发生在映射批准之后，来源和映射当前仍有效；同时重新核验当前来源/
目录授权、采集回执及成色归一规则。纯内容摘要不提供这些授权。

通过两个专用读取角色实际采集后，服务调用计算内核。插入记录、授权审计及审计头更新
在调用者同一事务中提交；出现异常由调用者回滚。相同请求恢复原记录，两条并发相同
请求只保存一次；相同键配不同内容会拒绝。不同来源批次可保留各自截止，旧记录不被替换。

保存截止不表示对账已批准，也不生成库存。计算候选中的原始能力标志保持原样，外层
`recorded=true` 只说明不可变采集事实已经记录。正式 reconciliation 状态投影、解释、复核
和业务角色 API 仍未实现。

## 数据库核验与锁范围

新表只允许直接 schema owner 写入，API、projector、Edge 均未获新权限；备份角色仅
SELECT。实际读取了函数完整源码摘要、所有者、SECURITY INVOKER、固定 search_path、
仅所有者 EXECUTE ACL、两个 ALWAYS 触发器和六角色表权限。UPDATE/DELETE/TRUNCATE
即使由普通 schema owner 执行也被守卫拒绝。

守卫核对批次、映射、会话、当前总部权限、授权有效时间、上海日期、原始摘要和审计绑定。
此外直接读取真实账本前缀，逐条核对交易、流水和账户/库位/组织事实；从真实来源 origin
及本地流水独立重算仓库/物料/成色的左右数量、差异及排除状态数量，不接受报表自报的合计。

服务按参考目录 → 库存账户 → 账本 head 顺序锁定，在本地采集与入库提交期间固定 head；
实际并发写 head 的连接被锁超时拒绝。参考目录 SHARE 锁也阻止新增/改名造成范围变化。
**这会短时阻塞库存写入**，正式接入前必须补完整锁顺序、整项期限和规模/并发性能评审，
不能把本批小型合成验证当成 500 用户验收。

## 实际场景与历史保持

- 三份截止各绑定一个新的已发布来源批次，均记录游标 3；每份五个比较明细，经 SQL 守卫和
  独立离线算术复核一致。原始来源时间没有改成读取时间。
- 在测试传输边界改写报表数量并重算全部相关摘要，实际数据库仍报 `comparison mismatch`。
  同样改写一条本地流水并重算摘要，被 `ledger facts mismatch` 拒绝；均无部分截止或审计残留。
- 来源撤权后不能新建截止，旧请求仍可恢复原结果；日终映射撤销后行为相同。旧来源、映射
  和原始计算证明重新核验，不能把恢复历史当作恢复当前授权。
- 会话撤销后，即使是原请求也拒绝操作者恢复；内部历史证明仍可核验。
- 日期错误、批次摘要错误、客户端额外快照字段、请求冲突、无权角色和不可变表写入均拒绝。
- 仅截止、授权 audit_events 和 audit_chain_heads 因截止创建而变化。源发布、映射批准/撤销
  和测试会话撤销分别产生各自事实；六张库存表在整个流程前后摘要一致。

复现旧错误并核验修正；缺目标仓、重复非目标仓及非目标 origin 仍拒绝。5 项新测试及原
29 项适配回归均通过；其中本地时间调整明确只属于纯测试，不能当作新的实际采集证据。
7.93 的原代码及证据未改写，修正差异另存于本批，后续正式集成须采用扩展后的版本。
