# 原启动请求永久终结与恢复（7.71）

本批补齐 7.70 的长期未知启动请求处理。公开首页仍为“交流备件知识大全”，星星入口
保持 `/xx`；两端新启动开关仍为 false，小程序私有业务页仍未注册并从公开包排除。
这是候选代码与本地隔离验证，未提交、推送、部署或执行外部业务写入。

## 实现与迁移

- 新增 0128 迁移和不可变 `opening_start_command_seals`。终结绑定本人、授权版本、区域、
  历史发布批次及原追踪号；唯一命名空间是操作者账号与原请求，换任务正文或幂等键也不能
  绕过已提交的终结。不保存原启动正文或原幂等键，不补写历史任务的未知结果。
- 原启动和终结共用库存账本锁。启动先提交时返回已存在的原任务，不产生终结；终结先
  提交时，迟到启动永久拒绝。应用预检与持锁后的再次检查之外，数据库 ALWAYS 触发器
  在 COMMIT 检查相斥证据，不能靠绕过 Python 检查产生任务。
- 终结必须通过当前区域管理权限和账号身份，插入及提交使用数据库实时时钟重新验权。
  授权等待期间撤销、角色在事务期间到期、缺少完整审计等情况均拒绝整批提交。
- 终结记录与完整库存审计绑定，查询验证审计链前缀及准确坐标，重复请求返回同一结果。
  审计动作使用独立的 `opening_start.sealed`，保留现有盘点任务审计完整性规则。
- API 仅获得新表 SELECT/INSERT；两个内部函数不对运行角色开放 EXECUTE。启动检查
  固定函数体、私有 ACL、六个触发器及两个完整唯一索引；UPDATE/DELETE/TRUNCATE 均受限。
  0128 空库可往返；存在终结事实时拒绝降级，不能删除历史证据来达到旧版本。

旧 `/v1/stocktakes/opening/start-result` v1 保持兼容。新客户端使用
`GET /v1/stocktakes/opening/start-command-result` v2，明确区分 `found`、`sealed` 和
`not_observed`。`POST /v1/stocktakes/opening/seal-start-command` 仅接受准确原请求坐标，
请求头固定绑定原追踪号和 `opening-start-seal:` 前缀，不生成新启动键。

Web 和小程序提供“终结原启动请求”。先查原结果，已有任务或终结时只恢复；未观察到
结果时必须由用户确认，才发送一次终结请求。无论 POST 成功、超时还是返回内容不完整，
都以独立的两次一致回读和当前验权为准。没有终结证明就保留原标记；取消、错人、错请求、
证据变化、隐藏或卸载都不能清理记录。终结完成不显示“任务创建成功”，也不自动启动新任务。

部署顺序必须先完成 0128 迁移及服务端版本验收，再部署使用 v2 的客户端，开关继续关闭；
部署与开启还受当前候选完整门禁及真实环境验收约束。
